# 客户售后申请与已发货设备选择

本批继承原 `create-after-sales.ts`、Store after-sales/devices API 和订单 `after-sales` React 组件，将其接入新 Gin / Astro。账户订单详情及订单确认页保留原展开式申请区、退货/换货/维修选择、商品数量/单台设备选择、原因、历史状态和提示；继续使用现有 Ant 组件与中英文文案。确认页可以提示未登录客户登录，匿名购物车凭证不授权售后。

新增 `GET/POST /api/store/customer/orders/:id/after-sales` 和 `GET /api/store/customer/orders/:id/devices`，通过现有签名私有桥传输。当前有效、已验证客户会话及显式 `customer_order_ownership` 是必要条件，不迁移旧账号，也不按邮箱认领。设备接口只返回该订单 shipped/returned 分配的原字段：设备/分配/行 ID、SN、主 IMEI、状态、替换关系及物流单号；不返回 EID/IMEI2、成本、仓库、来源或照片。预配/装包设备不向客户公开。

原业务校验：订单不能 canceled/draft；条目不能重复或超购买数量；数量为1—10000整数。未发货的 managed SKU 可不选设备申请退货，数量不超过购买数量减去未取消已发货包裹数量。对已发货 managed SKU，退货/换货/维修均要求数量与所选设备一一对应，且每台属于该订单行的 shipped 分配；非 managed SKU 不接受设备 ID。履约数量复用现有 scalar/raw 数值解析和有理数比较，忽略取消/软删除包裹，不转浮点。同一有效包裹关联多个订单时拒绝数量判断。

`0068_customer_after_sales.sql` 添加原售后事实表、新客户操作收据及默认关闭的申请开关；本次已提交迁移累计67。MySQL 生成列唯一索引约束每个订单最多一笔 pending/processing 申请，完成/拒绝或软删除后释放该槽。事实表 customer_id 不强绑新账号，保留后续历史导入形态；历史客户 ID 不因此取得新会话权限。

申请在当前账户检查、设备全局锁、当前订单锁与显式归属检查后执行，与现有设备发货写入串行。保存请求、操作收据及审计同事务，末尾失败全部回滚。operation_id 使用 UUIDv4，绑定当前客户、订单及不可变规范请求；同操作并发只提交一次，新 UUID 也不能创建第二笔待处理申请。新申请关闭时可读取历史及重放已保存收据；重放仍须当前会话和归属有效。Origin、客户 CSRF、JSON 类型与16KiB上限沿用私有边界；嵌套重复字段、未知字段、null、客户端 title、非整数数量和尾随JSON均拒绝。

Astro 响应严格投影；POST201 仅在售后申请路由接受。前台在结果不明时保留相同 UUID/内容并冻结编辑，重试恢复原收据；刷新可查询已保存申请与状态。订单主信息读取独立，售后加载失败不影响其他订单内容。

验证使用独立源码快照、自有受限 MySQL/Redis、实际 Gin 与 Astro。SQL 覆盖未发货退货、已发货三种类型/设备校验、同 UUID 和不同 UUID 并发、关闭后新申请、暂停时恢复、取消包裹不算已发货、跨账号、非法HTTP/CSRF及晚期审计失败回滚；浏览器覆盖真实提交、提交已落库但响应丢失、同 UUID 恢复、刷新后历史和中英文390/1440布局。

此处完成的是客户申请入口与事实持久化。原 `update-after-sales` 的后台审核、收回设备、检测/维修、替换出库、真正退款及完成门槛仍需迁移；申请事件通知邮件也尚未接入。本批不产生真实退款、设备收回、承运商预订或邮件，不将售后或整个前台标记为闭环完成。
