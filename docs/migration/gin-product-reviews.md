# 商品评价：原流程、原生事务与 HTTP

2026-10-31。本轮完成后台事务和 HTTP 层，尚未完成商品页、本人订单页、React Admin 审核界面、历史评价导入或真实浏览器联合。不能据此关闭 C01/C02/C03 或整个迁移目标。

## 原有业务契约

来源为 `medusa-store/apps/backend/src/workflows/product-reviews.ts`、`src/lib/review-orders.ts`、`src/api/review-validators.ts`、Store/Admin 的 `product-reviews` 路由及 `src/admin/widgets/product-reviews.tsx`。前台来源为 `medusa-store/apps/storefront/src/modules/products/components/product-reviews` 和订单评价组件。普通信息页 `/reviews` 仍是原介绍页，不新增独立全站评价系统。

- 登录客户可不关联订单提交普通评价。关联订单时必须是本人订单、当前版本包含该商品，状态不是 canceled/draft，且至少有一个付款集合，所有集合均为 completed。原实现没有先发货/签收要求。
- 商品必须已发布并在当前可信店铺的销售渠道内。请求不能指定店铺、渠道、客户、公开作者、审核状态或购买验证标记。
- 每位客户对同一商品只有一条未软删除评价，待审核和已拒绝评价也占用该资格。新评价状态为 pending；作者仅截取当前客户 first_name，不公开姓、邮箱、客户或订单 ID。
- 星级为整数 1–5；标题去空白后 2–120 个 JavaScript UTF-16 单位，正文 10–3000。新增 Go 边界保留这些长度及空白语义，拒绝重复键、未知字段、null 和额外 JSON 文档。
- 公开页只返回 approved 且未软删除的评价，按 created_at DESC/id DESC 分页；默认 5、最多 20，并提供全量五档分布及加权均值。审核可在 pending/approved/rejected 三态之间切换。

## 原生持久化和事务

显式迁移 `0094_product_reviews.sql` 建立评价、原子命令回执及 version=1 运行门，读写默认均关闭。保留原始 ID、时间、软删除、customer_id/order_id 历史引用；额外的 account_id 仅指向新客户账户。生成列将 `legacy:` 和 `account:` 唯一性分开，禁止用同邮箱或历史客户 ID 继承评价/订单归属。历史评价导入尚未实现，不能把隔离测试插入的历史样本当作源数据导入验收。

`internal/productreviews` 实现公开读取、本人购买选择/订单评价上下文、提交与员工审核。复用商品模块的发布/店铺范围判断；客户层复用既有账户锁、两次 Redis 会话核验和当前权限版本。关联订单仅通过 customer_order_ownership 取权，拒绝依据 orders.customer_id 或邮箱判断本人。

提交参与者必须处于调用方 SQL 事务内，拒绝 autocommit；新增评价和 durable 回执一起提交。账户锁使同客户并发串行，数据库唯一约束提供最终保护。同 UUID/同参数可恢复原结果，改参数或跨客户重用冲突；写门关闭后仍允许当前合法客户恢复自己的已提交回执。审核要求当前 product.read/product.write，锁评价并验证原状态指纹；状态变更与记录旧状态的回执同事务。重放仍重新验证当前身份与权限。

评价不写库存、预留、设备、价格、付款、发货或邮件事实。

## HTTP 边界

| 方法与路径 | 语义 |
| --- | --- |
| GET `/api/store/product-reviews?product_id=…&offset=0&limit=5` | 公开已批准评价及统计 |
| POST `/api/store/customer/product-reviews` | 当前客户提交，返回 201 `{review:{id,status,replayed}}` |
| GET `/api/store/customer/product-reviews/purchases?product_id=…&offset=0` | 本人订单选择及本人已有评价，固定每页 20 |
| GET `/api/store/customer/orders/:id/product-reviews` | 本人订单资格及订单当前商品的本人评价状态 |
| GET `/api/admin/product-reviews?product_id=…&offset=0&limit=5` | 当前具备商品读取权限的员工读取审核列表与每条 revision |
| POST `/api/admin/product-reviews/:id` | operation_id/expected_revision/status 原子审核 |

客户路径复用签名桥、专用客户 Cookie、Origin/CSRF 和 private/no-store 响应。Referrer-Policy 在桥校验之前设置，签名被拒绝时也保留隐私响应头。Admin 路径复用现有管理员认证和 CSRF 中间件。Astro 客户传输已加入这三条专用路径，购买选择只允许 product_id/offset；拒绝错误成功状态和评价接口设置会话 Cookie，语义错误只透传状态匹配的白名单代码。

## 同一新购物订单的原生浏览器联合

上述连续联合现已通过独立本机 MySQL/Redis、94 项迁移和真实 Chrome，见 [原生联合报告](product-reviews-native-joint-report.json)。四个客户均实际注册、验证、登录、从商品页加入新购物车并付款成单，再在已付未发货阶段提交评价。中英 × 390/1440 各一组：两条从商品页取消可选订单关联后提交普通评价，两条从本人订单提交已验证购买评价。业务 API 使用实际 Gin handler，没有用模拟响应代替提交、审核或公开读取。

每组都故意丢失首次已提交的成功响应，检查字段和取消操作冻结，再以相同 UUID/参数重试提交及审核。验证待审不可公开、重复提交 409、外人订单 404、公开字段隐私、内容转义、精确平均分和本人状态；首组另外经过拒绝→待审→批准，SQL 最终确认 4 条评价、4 条提交回执和 7 条审核回执。评价操作前后按全列指纹核对库存、预留、价格、设备分配、付款和捕获未变。随后继续原购物测试的平台配货、仓库解除/重新装包/发货和本人设备、物流、通知，原断言全部保留，浏览器异常为 0。

测试准备仅适配独立副本的测试接线、端口、数据库和 Redis 前缀；生产实现保留记录的源文件字节。Admin 使用独立 Vite 缓存。中文订单页 Ant 按钮会自动插入空格，测试定位允许“取 消”，仍验证结果未知时不可取消；没有为通过测试修改生产按钮。源码及日志、截图 SHA 见报告引用的证据清单。四组通过后，专用数据库、两个用户、Redis 键和监听端口均已清理。
