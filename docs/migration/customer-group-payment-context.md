# 付款冻结后的客户组变化

本轮补独立 Gin/MySQL/Redis/Astro 付款上下文子流程：会员价100 EUR、会员优惠10 EUR、配送7 EUR和25%税率下创建121.25 EUR付款，再移除成员。保留原付款期间不能静默改成渠道未确认的新金额；商品修改被拒绝，原CREATE重放仍只确认同一笔冻结付款。

显式切换语言时，既有付款上下文协调器按当前成员关系重新计算整个购物车，退役旧付款、清除失效会员价和优惠，并保存当前报价。取消完成后如果价格漂移，则保留原指令供用户恢复；补偿恢复原地区、语言和原付款快照。随后再次显式保存新上下文才采用当前报价，清除失效会员价和优惠。

两条固定路径为 `group-save` 和 `group-restore`。前者丢保存成功响应、刷新沿原UUID恢复，再创建当前158.75 EUR付款；后者取消期间将基础价格变为122，使保存返回报价冲突409，再经显式恢复创建原121.25 EUR替代付款，并丢恢复成功响应、刷新沿原UUID恢复。之后以新的显式保存指令清除会员优惠，再创建当前161.25 EUR付款。都核对每一步渠道事件、当前有效付款数量、版本及原订单/库存/实收/邮件保护指纹。

```powershell
node retail/scripts/test-context-payment-joint.mjs --scenario group-save --scenario group-restore --scenario retired-edits --matrix
```

运行器的 `CONTEXT_BROWSER_EXECUTABLE` 可显式指定已安装的Chromium；使用满足项目版本要求的Node。每次冻结源码、构建一次，再按场景组合执行。`retired-edits`回归已有配送/税额/优惠的商品修改，以及商品、优惠、新付款分别丢响应后原命令恢复，不执行整条订单履约流程。

## 环境及范围

隔离验证器原先将迁移数量写死为105。本轮改为严格匹配当前完整SQL文件数量，仍使用正式迁移解析器和执行器。构建只链接依赖包，`.astro`、`.vite`及`.cache`由独立目录持有；Go使用`-trimpath`，避免每个冻结目录产生带不同绝对路径的缓存，临时编译文件也写入独立构建卷。构建前检查独立卷至少2 GiB可用空间。

目录被链接到其他Windows盘时，先解析真实路径；若依赖位于不同盘，则按锁文件SHA256建立同盘依赖副本，再仅链接包目录。副本完成才写就绪标记，不复制运行中的构建缓存。这样避免Astro内部资源出现无法解析的跨盘相对路径，同时保留主项目依赖及服务。

会员组、价目表和优惠配置由明确的独立SQL夹具准备；成员变化使用受私有夹具Key保护的控制路由，未声称本轮重新验收Ant组管理操作。真实账号会话、购物车绑定、优惠、付款创建/查询、保存及恢复均走正式接口和数据库事务。仅外部付款适配器为人工实现，没有新的实际Mollie付款、扣款、订单或履约。
