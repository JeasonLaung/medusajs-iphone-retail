# 回收问卷与申请输入契约

本次承接原 `CreateBuyback` Zod 校验器和 `sell-flow` 的状态规则，供真实问卷页面及 Gin 事务命令继续使用；没有开放申请 HTTP、写入申请表或挂接问卷路由。

Gin `ParseSubmission` 接收原七个顶层字段，保留 1–10 台设备、UUID、联系信息、退回地址、两个明确同意值及每台完整检测答案。地址二行缺省为空字符串；联系信息/型号按 JavaScript 空白规则 trim，长度按 UTF-16 单位计数，包含 BOM、emoji 边界。容量在提交快照内保留原值，由后续商品/价格查询规范化。跳过的屏幕/背面字段按原 schema 保留有界字符串，不能错误套用局部估价校验而拒绝原合法提交。

输入继续使用现有严格 JSON 解析：16 KiB 字节上限、UTF-8、嵌套深度、数组边界、重复键和精确字段名检查。该字节上限是新增的传输边界，原 Zod 单字段 schema 本身没有总字节上限。没有从浏览器接收 customer_id、email、product_id、参考金额或状态。身份、当前商品/容量资格、当前报价、提交去重及事务提交均属于后续服务端命令的职责。

`sell-questionnaire` 保留原 sessionStorage key、部分恢复顺序、布尔/null 检测槽位、互斥 none、屏幕与背面跳题、首个缺失问题守卫、型号/容量路由和改选后的依赖清空。不迁移到 localStorage，不改变原问卷的存储范围。路由调用方必须先校验路径，并在原页面的 ready、URL 与状态同步条件满足后调用守卫；这些函数不自行导航或访问浏览器存储。

128 组实际原 Zod 校验对照（40 接受、88 拒绝）及 Go 精确归一化输出通过，另有重复键、字段大小写、尾随 JSON、无效 UTF-8 和输入体超限拒绝。恢复测试直接运行原 TS `restore`，覆盖损坏存储、无效型号/容量、部分检测和互斥选项；路由/守卫/改选清空另有明确预期用例。Go 全量、163 项前端测试和 Astro 345 文件检查通过（0 错误、0 警告、5 条既有提示）；旧 health/app/sell 返回 200，最近服务日志未见错误。

下一阶段仍需接问卷组件、保留导航进度和表单，完成申请事务、认证/CSRF/幂等、列表详情和照片，再接审核/设备/报价确认/付款退回。完整回收业务尚未验收。详见 [证据报告](buyback-submission-contract-report.json)。
