# 订单设备装包与数量库存

订单详情新增 Ant Design「创建配货包裹」抽屉，选择已预配设备后创建真实履约、履约行和订单关联。沿用原页面及读取入口；预配入口、普通解除及已存在的履约证据展示保持原行为。

对应原 `workflows/device-operations.ts` 的 fulfill / save_allocation 新建包裹分支。设备预配不扣数量库存；装包创建履约时扣一次，后续发货不能再次扣。本批承接已预配设备的装包，不将未完成的发货、取消或仓库员工履约宣称为闭环。

## 权限与条件

- 复用显式 `order.allocation.write`，另外要求 `order.read`、`order.payment.read`、`device.read` 和 `order.fulfillment.read`。warehouse/supplier 不能使用全店入口；既有角色不自动增加授权。
- 新增0066迁移，累计65个已提交迁移。`order_device_packing_runtime` 默认关闭，须与设备身份/命令、预配开关一起显式启用；不自动开启真实数据库写入。
- 使用当前版本的成交行与未取消、非草稿订单；至少一个支付集合且每个均 completed。不能以 authorized 或手工改界面状态代替实收。
- 每次1—200个不同预配分配，均须reserved、无fulfillment_id，对应设备仍是sale/reserved且SKU、来源、位置一致。一个包裹只允许同来源、同仓库设备。
- 订单的第一个当前配送方式是来源工作流的默认配送方式。当前接入 `manual_manual`，不支持的渠道明确拒绝，不改用其他手工渠道，也不伪造外部订舱或标签。服务仓库、提供商、服务集合、商品配送档案与销售渠道关联均重查。

## 原子事务

先锁当前账号与授权，再锁设备全局运行时、订单及库存运行时。库存运行时使用排他锁，既有库存写入器在其前持有共享锁，从而避免装包迁仓/拆分预留与结账或库存编辑同时执行。业务行和存在性校验使用当前锁定读，不能在等待库存写入后继续使用旧Repeatable Read快照。

每个选中成交行核对剩余可履约数量、SKU的唯一单位库存关系、当前设备身份和渠道。订单行存在多笔预留、绑定错误、预留不足、库存层缺失、迁移差异或数量库存不足时拒绝；不通过装包修复历史差异。

装包库存使用精确十进制字符串。扣减包裹实际仓库的现货；有原预留时，从其原仓库扣减已消耗的reserved数量。部分装包保留原预留ID、原仓库和剩余数量；全部消耗则软删原预留。无原预留时仍需实际仓库存在可用库存。当前在途数量不会变成可用现货。scalar与raw数量同步写入，不经过浮点数。

同一事务复制订单收货地址到独立履约快照，创建包裹、行、订单关联，保留成交标题/SKU/条码及精确数量，累加当前成交行fulfilled_quantity，更新订单时间，绑定分配并将设备与分配转packed，记录pack事件与不可变收据。任何末尾失败都回滚以上变更。

## 接口与界面

GET/POST `/api/admin/orders/:id/packing`。GET返回已预配设备、默认配送方式、启用/实收状态及当前摘要，不返回库存差异、收货地址或成本。POST复用严格配货请求结构：operation_id、expected_revision、action=`reserve`、ids；此处ids是已预配分配ID。保留Origin/CSRF、JSON类型及有界输入验证。

摘要覆盖订单、地址、付款、当前分配/成交行、配送方式及库存/预留。冲突要求重新读取。同账号、订单和原请求的重放返回原包裹ID，不再扣库存；重放重查当前权限、订单、包裹与分配/设备/成交行存在性。未知响应时界面固定原批次和UUID，只能重试本次保存。

## 验证与剩余范围

隔离SQL验证默认关闭、付款条件、同操作四并发只建一个包裹、末尾收据失败整体回滚、跨仓部分预留、精确scalar/raw及fulfilled数量、无预留扣减、多预留和差异拒绝、混合来源、库存不足、不支持渠道拒绝、条码快照、重放/权限撤销及已删目标拒绝。

真实浏览器沿预配两台→装包一台→刷新读取路径核对React/Gin/MySQL/Redis，验证剩余设备、包裹持久化、中英及390px；SQL另核对真实库存和预留余量。证据为 `order-packing-report.json` 与 `order-packing-joint-report.json`，后台25项浏览器回归覆盖新增装包的未知响应重试与权限更新。
