# 买赠数量与金额分摊

2026-10-29：独立 `totals.AllocateBuyGet` 为已由服务器完成buy/target规则筛选的购物车行计算买赠。输入包括code、fixed/percentage、最少购买数、每轮赠品数、最大赠品数（缺省1）、原subtotal/quantity、buy/target成员资格，以及按code分别保存的数量消耗和共享优惠余额。当前组件不查询SQL，不提交事务，不将浏览器提交的资格当作可信上下文。

## 保留的原行为

- buy与target分别按整行subtotal降序稳定排序。购买侧先使用不具备target资格的行，避免将唯一可赠送商品占用；各组内部保留原价格顺序。同价保留输入顺序。
- 其他code的buy记录只从buy候选数量扣除，target记录只从target候选扣除；同code的旧数量记录不参与本次资格扣减。每轮选择后，buy与target合计占用同时扣除本次两套剩余数量，避免单轮同一件既购买又赠送。结果替换当前code的累计数量列表，保留其他code记录。它不等同于一个跨角色全局数量预留器，不能声称原规则禁止所有跨code跨角色复用。
- 先凑够最少购买数，再从target中扣除本轮购买占用，必须凑够完整apply_to_quantity才应用。原最大额度在同一批次收集多个target行时不逐行递减，因此某些多行批次可超过剩余额度；该既有边界也固定在fixture中，未擅自改成另一种规则。
- fixed按赠送单位数乘金额，并以subtotal/quantity的单位基数封顶；percentage先乘基数再除100。共享既有优惠不减少本分支的目标基数。percentage大于100、零折扣仍消耗本轮资格数量等行为与原函数一致。它不沿用标准商品促销的epsilon或含税换算，也不因is_discountable字段自行增加过滤；最终资格应按原buy/target规则筛选。
- 同行跨轮金额汇总成单个动作，按首次产生正金额的顺序输出。循环最多1000轮，返回显式IterationLimit。上层命令必须拒绝该截断状态，不可静默保存部分结果。空items保留所有原code记录，不写空记录。

## 精度差异台账

旧buy-get在把金额加入共享map时调用toNumber，动作本身却保留BigNumber。人工例：subtotal=27021597764222979、数量3、fixed优惠9007199254740993，原动作是9007199254740993，但共享余额变成9007199254740992。新引擎沿用项目精确金额要求，在动作与共享余额中都保留9007199254740993，避免后续促销基于已经丢失一位的余额计算。这是明确记录的精度修复，不宣称该余额与旧浮点输出逐字相同。常规20组对照不包含这种精度差异；fixture另有precision_exception固定原始损失与要求的精确余额。

## 可重现验证

`node retail/scripts/capture-buy-get.cjs --check` 调用实际安装的 `getComputedActionsForBuyGet`，固定20组独立预期与buy/target数量、共享余额，另验证上述精度差异和原1000轮警告。不初始化应用、不访问数据库/provider。金额预期为独立人工整数，共享余额以BigInt相加；来源buy-get、usage、promotion-rule文件有SHA。fixture见 `fixtures/buy-get.json`。

Go逐项核对20组金额/数量/状态，包括购买与赠品相同、购买优先保留赠品、不同code消耗、同code重算、最高金额赠品、同价稳定、批次额度、零值、空行、已折扣金额、循环上限。另验证超安全整数精确余额、非法配置/重复行/无效金额/超限输入不产生部分结果，返回map与嵌套slice不共享。Go全量测试、totals/promotion静态检查通过。
