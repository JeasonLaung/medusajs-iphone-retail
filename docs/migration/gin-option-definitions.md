## 已核对的来源行为

原 Dashboard 的 `routes/product-options` 提供独立定义列表、新建、编辑、详情及选项值删除；新建/编辑提交 `title`、完整 `values` 和可选 `ranks`。编辑表单按已有 rank 排列值，空 rank 排到末尾。定义及值的 metadata 页面也存在，不能因先实现标题和值而宣称该来源已全部覆盖。

安装的原 product 模块 `services/product-module-service.js` 的 `updateOptions_` 按值的原文字匹配已有 ID；遗漏的旧值属于删除。保留值未传 rank 时保留原 rank；新增值由事务生成新 ID。`validateOptionValuesNotAssociatedWithProducts_` 拒绝删除任何仍有商品关联的值，不要求该值已经用于 SKU。该检查按未软删关联行判断，不能额外限定为已发布商品或活跃 SKU。

删除整组则使用 `repositories/product.js` 的 `canDeleteProductOption`：未软删关联行所指商品及定义均未软删时拒绝删除；仅关联软删商品不构成这一阻止条件。该规则与单个值的删除检查不同。共享定义不能转为专属定义。

原 `models/product-option.js` 还有未软删共享名称的唯一索引；同名专属定义不受该索引限制。`schema_plan.json` 已将这一完整标题索引、以及 `(option_id,value)` 的未软删唯一索引列为 hold，不能因为事务中做了查询就标记物理约束完成。只读核对既有真实源快照得到163组选项、2组活跃共享定义、120组活跃专属定义，共享标题无重复，最长5字节；一组最多6个未软删值。此审计仅证明这份源快照，不证明目标导入或新约束已验收，见 `logs/gin-migration/option-definitions-source-audit.json`。

源码路径及 SHA256 记录于 `logs/gin-migration/option-definitions-core-report.json`。原 `product.options` 仅负责商品选值和专属组维护；独立共享定义管理不能借其较窄的 SKU 占用检查代替上述保护。
