2026-10-29 用户明确：当前需要前台购物/回收闭环（包括支付），产品、SKU、仓库（含仓库用户）、库存、配货、通知邮箱；随后补充“整个前台的功能能够闭环”。本文件覆盖之前以全部 Medusa 后台业务为当前目标的执行顺序，不删除历史证据或擅自丢弃已有实现。

## 边界

本阶段交付独立 Gin + React Admin + Astro，MySQL + Redis。整个现有前台的页面和交互严格继承；按源码已存在的功能迁移，不按通用商城想象新增功能。前台依赖的后台处理同属本期，不能前台挂入口却将其后台动作放到后期。旧账号不迁移，新账号不按同邮箱继承历史私有业务。开发与测试继续隔离，不操作部署服务器。

前台来源是 [路由表](frontend-routes.md) 的32个页面模式、36个页面实现和7个非页面handler，以及 [前台基线](frontend-baseline.md) 的公共交互与状态；不是只验收页面HTTP200。演示/UI页面保留原演示性质，不因“闭环”扩成新业务。没有在来源确认的独立收藏系统不因通用商城习惯加入；若原源码有非页面入口的交互，也需随页面一起迁移。

后台延后：独立供应商门户/完整供应商管理、营销活动/群发/通讯录CRM、内部AI工具、SEO自动生成及独立运营报表等。已有前台博客/帮助/评价/SEO输出、基本供应来源、单台设备身份和交易关系仍保留；若是本期流程必要依赖则纳入。售后不可整体延期，因为当前前台已有订单售后入口。

## 支付与回收的准确含义

购物支付承接当前实际使用的 PayPal、PayPal Card、Mollie 入口及返回/通知/退款依赖。先把前台可操作流程和后台订单打通，再围绕需要的付款安全与故障恢复补齐；不能只持续建设未接到页面的适配器，也不能用手工标记已付替代在线支付。

原回收 `mark_paid` 是管理员在客户接受终价后记录 payment_reference；并没有自动向客户转账的API。第一阶段承接这条真实业务闭环，不能凭“包括支付”新增银行代付系统或声称人工记录已经完成转账。终价拒绝/申请退回、重拍、私有照片和回收设备关联都属于现有前台的完成条件。来源详见 [回收与邮件](buyback-and-mail.md) 和 [设备命令](device-commands.md)。

## 执行顺序

1. **正式可浏览网站（C01）**：将已验证组件接到真实Astro路由和Gin目录数据；先交付首页→列表/搜索→商品→购物车的真实导航路径，并补齐公共内容/语言/页面外壳。页面状态逐项登记，不增加独立后台工具。
2. **账户、商品和仓库运营（C02—C05）**：补新客户/员工、商品SKU编辑、仓库及权限、库存与设备入库，确保后续交易使用真实本期数据。每一模块配实际Admin界面和前台结果。
3. **购物交易及配货（C06—C07、C10必要通知）**：以完整购物路径连接现有计算/预留/付款组件，验证付款后唯一成单、仓库员工配货发货和客户订单查询；通知随交易交付。
4. **回收闭环（C08、C10必要通知）**：完整客户申请与后台处理串联设备入库、终价、付款记录/退回，各状态前后端同时验证。
5. **前台剩余功能（C09及C01/C02剩余状态）**：售后/评价/订单转移等按已有来源逐项闭合；必要退款/换机与库存/配货/邮件一起交付。
6. **本期联合验收（C11）**：逐条验收所有32页面模式与7 handler、登录前后/语言/窄屏及真实隔离数据；用户与后台操作能完成对应流程，不因单项测试通过宣称全站完成。

次序允许按依赖交叉，但本期范围不得再由未完成的全量后台清单自动扩大。一个交付完成后优先推进下一个可操作流程，而不是横向补齐全部历史后台能力。Ant Design组件用于新Admin，图表如需展示使用ECharts；前台原样继承。

## 整个前台的闭环标准

用户再次明确“整个前台的功能能够闭环”。本期验收覆盖现有前台全部实际功能；购物和回收是核心路径，账户、地址、订单查询、售后、评价、通知、公共内容与页面外的交互同样需要完成。后台实现优先满足这些前台功能所依赖的操作，并保留已明确要求的产品/SKU、仓库及仓库用户、库存和配货能力。

逐个核对32个页面模式及7个handler，并在各项证据中记录实际操作与结果。登录前后、中英、桌面/移动、刷新/返回、加载/空数据、失败/重试与无权限状态均随相关功能验证；跳转后没有实现、按钮只改本地状态、使用模拟API或仅HTTP200都不足以闭环。原界面布局和交互沿用现有前台，不能以功能实现为由整体改版。

注册必须最终能收到并完成验证邮件，购物必须能付款成单并由仓库配货发货，回收必须能由客户提交并由后台处理到终价、付款记录或退回，客户可查询实际进展并收到对应通知。上述联合路径均通过独立Gin、MySQL和Redis运行，不依赖Medusa服务；支付与邮件按隔离测试条件验证。当前各项仍按表内缺口标为未验收。

## 验收规则

- 每条C项记录：源码来源、实际Gin/API与页面入口、数据/权限条件、已验证步骤、仍缺步骤；只有辅助函数或模拟数据预览时状态为局部实现。
- 核心联合用例：新注册与验证→购买付款→后台实收订单→有权限仓库用户配货发货→客户查看；新注册客户回收→照片审核/收货→终价接受与付款记录（或拒绝后退回）→收到对应通知；前台售后处理与退款/维修/换机。
- 隔离数据库/Redis验证并发、越权、失败回滚及重复提交；浏览器验证原前台页面与状态，后台用Ant组件操作真实Gin；支付沙箱和邮件测试收件人不影响真实客户。
- 所有必要功能完成前保持本期未验收；不折算文件数/迁移数/测试数为完成百分比，不要求延期独立后台功能先完成。
