# 真实支付数据隔离 MySQL 演练

2026-10-27。使用已固定 v2 快照，在独立 MySQL 临时库验证[支付完整行转换](payment-history-conversion.md)与[同事务操作账本](payment-history-import.md)。结果见 [计数及实现哈希报告](payment-mysql-rehearsal-report.json)。这是支付子图演练，T006/T018/T035 与全域迁移均未验收。

## 实际执行范围

`rehearse-payment-history.py` 不接受目标 DSN、源数据库或服务器参数。它要求 Git 忽略的固定快照及与审查报告一致的 159 表 DDL，编译专用 Go 测试程序后，创建带唯一所有权标签的 MySQL 8.4.11 容器：禁网、无公开端口、1 核、768 MiB 内存；数据库在 512 MiB tmpfs，私有快照通过 stdin 写入 128 MiB tmpfs。程序本身不含真实数据，放入可执行的容器目录；此主机 tmpfs 禁止执行，因此不在其中运行程序。

Go 在任何目标写入前验证全部 159 表、27,140 行的记录结构、顺序、计数、footer 和固定 SHA，并运行全域关联校验。375 项已知历史缺失引用保持失败，88 个物理外键没有缺失。本演练只暂存有证据的付款子图，不把其他关联问题视为已解决。

2026-10-28 更新：目标从空库执行全部 20 个正式迁移并验证重放（包含 0019 的 8 张支付表/83 来源列及 0005 操作账本），不再执行完整 159 表审查 DDL。159 表审查文件仍用于离线来源模型校验。实际处理 23 个 payment_collection、21 个 payment_session、21 个 payment：集合 metadata 全部明确 SQL NULL；支付 JSON 按已审查入口密封，context 按不迁移旧账号的规则投影；不生成旧登录账号、不按邮箱授权、不启动 worker 或调用支付 provider。

## 已验证结果

| 检查 | 结果 |
| --- | --- |
| 首轮同事务暂存后回滚 | 65 个业务行、42 个 hold 均无残留 |
| 第二轮提交 | 23 集合、21 会话、21 付款、42 个 hold |
| 第三轮精确重放 | 全部通过；付款密文、源/目标 hash 和首次尝试标识保持原样 |
| 操作限制读取 | 三轮共 126 次，全部为 hold |
| 私有 JSON 独立解密读取 | data 42 个、context 21 个、metadata 19 个，与来源/投影逐字节相同 |
| metadata NULL 区分 | 会话 2 个 SQL NULL、付款 21 个 SQL NULL；另 19 个空对象保持加密 JSON |
| 旧身份资料投影 | context 中 34 个旧地址簿/绑定/默认标记字段被剥离 |
| 金额、时间、状态、业务引用等 | 集合逐列读回相同；付款通过导入器的完整行重放比较 |

付款金额的 SQL 比较显式 `CAST(? AS DECIMAL(38,18))`，不依赖字符串/数值隐式转换；新增人工反例把金额最后一位改为 `1.230000000000000001`，必须冲突。人工并发、密钥轮换、目标篡改等结果继续见 mysql-type-fixture-report.json，本真实演练不冒充这些人工场景。

新业务密钥只在 Go 内存生成，未落盘。报告只含固定字段名、计数、环境限制和实现哈希，无业务 ID、金额、联系信息、私有 JSON、密文、密钥或解密内容。结束时核对唯一标签并删除自建容器，私有源副本/目标表随 tmpfs 清除，唯一临时测试程序也删除；原固定快照、旧业务库及其他项目容器保持不变。
