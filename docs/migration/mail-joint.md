运行 `python retail/scripts/test-mail-joint.py`。可通过 `MAIL_JOINT_BACKEND` 指定隔离源码快照，通过 `ADMIN_TEST_NODE` 指定 Node 22。测试仅使用新建的人工管理员、客户及 `.invalid` 地址；不读取真实邮箱密钥。MySQL 单核、768 MiB，Redis 单核、128 MiB，临时数据存于 tmpfs，标签校验后清理。只向本机回环地址暴露临时 API 端口；不与原开发服务共享数据库或 Redis。

通过的路径：后台登录→添加发信邮箱与注册账户选择→刷新→空密钥编辑名称→原移动端注册表单提交→数据库验证邮件队列→读取后台选定邮箱配置→生产 Resend 组装与发送方法→原验证链接页面→新客户登录。测试进程仅替换最终 HTTP transport，校验固定 Resend URL、认证头、幂等键、发件人、回复地址及人工收件人，返回人工提供方编号；未向外部发信。队列已发送后不重复调用提供方。

另以人工失败订单邮件验证后台恢复：查看失败→取消确认仍为失败→确认重新排队→刷新保持 pending。后续直接核验数据库：尝试次数归零，只有一条重试审计，冻结正文与发件配置指纹保留，邮箱两次保存持久化，密钥保持加密，新客户已验证。

真实联合测试发现锚点 Popconfirm 可在该场景定位到屏幕外，导致确认不可点击。邮件重试改为 Ant Design Modal 确认，显示对应订单编号；不改后端命令和结果不明时的同操作重试机制。确认按钮须完整落在视口内，仍使用普通浏览器点击，不强制点击、不直接调用重试 API。
