# Gin 新订单编号

2026-10-29，购物付款后成单所需的事务组件。来源为 [现有编号规则](numbering-database-contract.md) 中已采集的订单触发器、整数展示号 sequence 及隔离 PostgreSQL 验证；不改变原前台订单号展示，不修改历史订单，不迁移旧登录账号。

## 已实现

`0046_order_number_allocator.sql` 新增独立单例，默认未初始化。应用启动不初始化、不发号；需要显式迁移后，由内部切换流程调用 `orders.SeedOrderNumbers`，提供冻结来源的整数展示号最后占位、10微秒时钟最后位置和审核快照 SHA-256。调用前须停止源写入，并完成目标历史导入；原 sequence 的 `is_called`、删除/回滚占位都要纳入，不能只取现存订单 MAX。

初始化同时核对目标全部历史订单（含软删除）的展示号与19位业务号，低于任何历史位置、未知格式、缺失证据均拒绝；超过一百万个不同业务号时明确拒绝，须先扩展切换读取流程，不截断后继续发号。同一原始种子重试是只读确认，即使之后已经发号也不会重置计数；不同位置或证据拒绝。SQL CHECK 固定初始化证据和计数下界。

`orders.AllocateOrderNumbers` 只接受调用方已有的 SQL 事务，在单例 UPDATE 行锁下生成下一整数展示号与19位业务号。新 tick 为 `max(last_tick+1, 数据库UTC微秒/10)`；上海 UTC+8 时间的14位年月日时分秒加5位 tick 余数全程整数运算。数据库查询不受会话时区影响；时钟回退不退号，INT 展示号溢出、业务号超出四位年份、单例缺失、SQL 失败均拒绝。

发号与订单写入必须在同一个事务；订单工作流须先核对幂等收据，再调用分配器，再保存订单，最后提交。分配器本身不提交、不调用渠道、不发邮件、不提供 HTTP。回滚也回滚表计数，未提交号码不可对外发布；不承诺绝对无缺号。历史导入不调用发号方法。

## 验证

```powershell
go test ./internal/orders ./internal/schema
python retail/scripts/test-admin-auth.py --order-numbering-only
```

Go 时间边界覆盖秒进位、上海日期进位、19位原文往返、非法日期/位数/非ASCII/负数与年份上界。隔离真实 MySQL 覆盖默认关闭、普通连接拒绝、软删除历史检查、种子回滚、同证据重试、不同证据/位置拒绝、订单写入后回滚、6连接60条订单并发唯一、未来历史时钟下继续单调发号、SQL失败、展示号溢出与单例缺失。测试没有连接真实客户数据库或外部支付渠道。

提交内容另在独立目录验证：45份正式迁移，不包含工作区尚未提交的0037支付通知迁移；完整 Go 包检查通过。隔离报告 [order-numbering-runtime-report.json](order-numbering-runtime-report.json) 记录实际源码哈希、人工用例结果及容器清理。临时 MySQL 禁网、未映射端口、单核768MiB，结束后按本次所有权标签清理。

## 尚未完成

本组件没有接通付款后的唯一订单快照、支付/实收记录、促销预算提交、库存预留、邮件、订单确认/私有查询页面。订单工作流还须将这些本地写入原子提交，并对已付款但库存不足提供可恢复结果，不能重复向渠道创建付款。正式冻结切换种子与业务数据联合验收尚未执行；不凭这项验证把购物闭环标记完成。
