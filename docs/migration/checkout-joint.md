# 结账到确认页真实联合验证

本用例连接正式 Astro 结账、付款结果和订单确认页与真实 Gin cart/catalog 处理器，在独立 MySQL/Redis 执行。只替换支付渠道适配器及其托管付款页面；不拦截或模拟 Gin/Astro 业务 API，不请求 Medusa，不连接真实支付渠道或发送邮件。购物车及商品行预先通过真实内部命令建立，因此本用例不代表首页选品到付款的全站验收。

验收路径是地址表单提交 → 配送选择及含税总额 → 付款方式 → 创建一次付款并进入复核 → 刷新恢复原操作 → 托管付款页面 → 待确认结果 → 适配器核实已付 → 唯一订单提交 → 原订单确认页及刷新。英文、中文和390/1440宽度分别使用新的隔离购物车。

浏览器逐步核对付款核实接口200及实际状态，避免将页面暂时显示“等待确认”误判为接口成功。成单后清除付款恢复描述，刷新仍可查看订单；再次完成请求返回同一订单，删除凭证后确认接口拒绝。数据库核对四个独立订单、每单唯一完成收据、每单一条库存预留操作与通知 outbox、精确实收金额158.75；夹具每个SKU消耗2.5库存单位，四单总预留增量为10。

测试的 `/__fixture` 控制入口只编译进测试二进制，需要随机密钥。标为已付只改变隔离适配器的后续核实结果，不写数据库的付款、订单或库存状态；业务记录由真实处理器提交。测试构造四个购物车，并在独立数据库增加其所需的10单位库存，不改动已有预留。运行期间临时统一公开目录和购物车为已注册 en-GB 语言码；相关开关及目录测试配置结束恢复。

复现：`python retail/scripts/test-customer-orders-live.py --checkout`。要求已有 Docker 引擎及 mysql:8.4/redis:7-alpine 镜像、Go、Chrome、前端依赖及 Node >=22.23.4，可设置 `STOREFRONT_TEST_NODE`。同一脚本默认运行账户订单联合，`--promotions` 运行优惠联合。

资源仍限 MySQL 1核/768MiB、Redis 1核/128MiB，数据库不发布端口，只发布随机回环 API；独立源码运行50项已提交迁移，排除工作区未提交支付通知改动。测试结束校验归属并清理容器、网络及测试二进制。结果见 [JSON证据](checkout-joint-report.json)。

该证据不包含真实渠道沙箱、支付通知与退款、订单邮件收件、仓库配货发货、回收、售后或完整商品浏览链。付款后修改商品/地址/配送/优惠的渠道协调仍待接通，不能视为购物或整个前台已经闭环。
