# Gin SKU 库存项关系管理

2026-10-31，承接原后台 `ManageVariantInventoryItemsForm` 及 `batchLinksWorkflow`：一个 SKU 可关联多个库存项，每项有独立的正数用量；普通库存项允许跨 SKU 共享。沿用现有库存明细抽屉，在其中增加 Ant Design 编辑抽屉，保存后重新读取明细。保持数量编辑、预留对账与设备页面原有入口和样式。

## 行为及边界

- `0092_catalog_variant_inventory.sql` 增加默认关闭的 `variant.inventory` 能力和独立审计表。管理接口为 `/api/admin/products/:id/variants/:variant_id/inventory-items` 的 GET/POST，以及 `/choices` 的 GET；继续使用现有员工登录、CSRF、商品读写和全局库存读取权限。仓库范围员工不能访问全店库存项目录。
- 库存目录按名称、SKU 或编号做字面搜索，每页 50 项；可继续加载，不截断整个目录。保留已关联但当前不可用的项，要求操作者明确移除或替换，不因查询结果缺失而静默删除。
- 使用完整关系清单保存，空清单表示明确解除全部关联。用量是字符串，正数、最多 18 位小数，写入 `DECIMAL(38,18)` 前精确规范化；不接受浮点 JSON，不四舍五入。
- 移除关系采用软删除；重新关联同一 `(variant_id,inventory_item_id)` 恢复原关系 ID 和创建时间。审计同时记录恢复前的已删除关系状态。此命令不修改库存项、库位数量、预留、设备或价格。
- 序列号 SKU 必须保留其原唯一库存项且用量为 1；其他 SKU 不能借用该设备库存项。SKU 核心编辑同时拒绝关闭已跟踪 SKU 的库存管理。**这是相对通用原关系编辑新增的保护限制**，用于防止 SN、数量及配货身份错位；普通库存项仍保留多项和共享语义。编辑与设备登记使用同一数据库锁序列化。
- 未启用库存管理的普通 SKU 可明确修复关联，启用后才生效；不会自动接管已有库存或恢复旧库存。
- 所有写入、SKU 修订号和审计回执在同一事务内；原 UUID 的重试恢复已提交结果。恢复回执仍重新核对当前权限；过期修订、外部 SKU、复用他人请求、不可用库存项均拒绝。发生不确定响应时表单保留原请求并禁用编辑，可重试本次保存。

## 实际验证

- 独立本机 MySQL 从 92 项显式迁移开始，随后同步共享工作区的 0093 通知迁移，共 93 项，并导入商品快照，新建测试员工和测试商品；不使用 Docker，不访问真实付款、退款或邮件渠道。
- 原生事务测试：4 个连接同请求仅一次实际写入；`0.123456789012345678` 精确保留；多项、共享、空清单、原关系恢复、失效项可见；修改和恢复两种操作在审计写入失败时全部回滚。实际库存、raw 值、预留、设备、跟踪与精确价格的前后指纹相同。搜索字面 `%`、52 项翻页、已软删除 SKU 的有效跟踪身份保护、旧修订、跨 SKU、关闭能力恢复回执、仓库范围及撤权拒绝均通过。
- 原 SKU 核心编辑原生事务回归通过，另验证已绑定实际设备的 SKU 无法解除库存管理。
- 真实 Chrome→React→Gin→MySQL/Redis→Astro，无模拟 API：填写 `2.000000000000000001`、添加共享项用量 `2.5`，公开可售量由 6 变为 2，价格保持 `129.123456789012345678`；明确移除后 Astro 显示缺货，恢复原关系后可售量回到 6。实物和预留记录前后完全相同。
- 浏览器故障注入在真实服务提交成功后丢弃首次响应，再由原请求重试并关闭表单；CSRF 和严格查询参数验证通过。中英文和 390px 抽屉检查通过，页面脚本错误 0。
- 后端全包测试、Go vet、Admin TypeScript 与差异空白检查通过。证据和源码摘要见 [验收报告](variant-inventory-native-report.json)。

主实例仍为原 86 项迁移和固定 API，未强行升级共享试运行数据库。该增量不代表 C03 或 C01—C11 整体完成；共享选项定义维护、条件价格、全站数据及业务联合验收继续开放。
