# 整车共享库存检查

2026-10-28。`inventory.ReadCartStock` 为真实加购命令提供完整候选购物车的库存观察。原单SKU目录可用量接口保留原契约，共用同一套正式SQL读取与冻结/预留差异过滤；本组件没有新增HTTP接口、预留或库存写入。

调用方必须在同一REPEATABLE READ事务中加载当前店铺渠道、有效SKU及配置完整性，并传入整车行项目与可信SKU标记。裸客户端不能选择manage_inventory、allow_backorder、渠道或仓库。当前组件检查已存在SQL事务，隔离级别由事务拥有者负责；它不证明商品已发布或属于店铺，也不代替购物车当前授权、版本与幂等控制。

- 每行的各库存项需求为精确 `quantity × required_quantity`，用38位/18小数SQL数量域与整数计算，拒绝超精度而非舍入。同SKU多行和跨SKU共享库存项都合计到具体库存项/仓库。
- 一行所有组件由同一个健康且关联渠道的仓库覆盖，不把分散仓库的单行库存拼起来。不同商品行可分配到不同仓库；不会要求整车必须来自同一仓库。
- 搜索稳定按候选仓数/行ID排序，并回溯仓库分配，避免贪心的失败被误报为缺货。最多1000行/1000可信SKU、1000渠道仓库、SQL关系总预算20000；分配搜索预算200000步，并检查请求取消。搜索未完成返回独立错误，绝不返回可购或确定缺货，也不交付部分分配。
- unmanaged跳过库存；配置不完整拒绝。backorder仍要求未删除的库存项和健康渠道库存层；冻结、预留合计差异不能被backorder绕过。普通行共享有限可用量，backorder在普通行之后分配并标识。该口径与既有`ApplyReservations`非backorder需求合计一致。
- 不使用设备序列号数量、incoming、外渠道/已删仓库与库存层。返回的内部行/库存项/仓库/精确需求分配带`json:"-"`，公开序列化仅state、can_fulfill。

加购只检查，不预留；本观察可能在提交后失效。成单必须重新核对实时渠道和当前锁定库存，再将可信分配转换为预留输入，不能复用旧观察承诺有货。当前尚未接入加购、成单或原Astro页面，checkout继续关闭。

单行同仓沿用当前Gin目录可用量口径。原Medusa准备函数按每个库存项分别返回候选仓，不能据本组件宣称已完整复现多组件跨仓的旧行为；该类SKU在正式加购接入前仍须核对确认/预留步骤并补充对照。本批证明共享库存合计与当前规划器正确性，不将人工穷举对照当作旧Medusa全行为对照。

验证包括单元中的共享需求/跨行仓库、backorder、取消/搜索超限，以及250组独立穷举仓库分配对照；实际MySQL测试使用正式26迁移和原目录人工fixture，验证逐行可购但整车超量拒绝、跨行两仓成功、只剩外国/在途库存不计、冻结及实时预留差异拒绝、18位小数末位精度，逐次对七张表做只读指纹。本批首次SQL运行在测试指纹误用无id表的排序列处失败，已改用冻结表复合主键排序；最终证据以报告源码SHA和整组重跑为准。

没有因此验收T032/T033。尚待实现实际加购事务/持久回执、服务端目录与价格选择、数量更新/删除、税费促销配送重算、结账和完整页面。
