## 入口与权限

`GET/POST /api/admin/orders/:id/after-sales/:request_id/devices/:assignment_id/service`。绑定真实订单、申请、原销售分配及当前设备，不能指定另一订单或未收回设备。读操作需要订单、设备、仓库、商品和库存读取；写操作另外需要 `device.intake` 与 `order.after_sales.write`。专用仓库作用域处理仍待实现，仓库身份不能借此进入全店入口。

0071 迁移新增默认关闭的处理开关及持久化收据，提交迁移总数 70；不自动向任何角色授权、不修改生产数据。

## 原有业务规则

- 设备类别为 returned / recycled，状态为 inspection / repair 时可检测。本批售后入口处理原订单关联设备，独立回收入库检测入口仍需随回收接入。
- 检测选择受库存管理且非超卖 SKU，必须存在单台库存关联、当前仓库来源；提供实际成色、电池、说明及最多八张可验证照片。
- 普通检测通过可改 SKU，设备进入 sale / available。处理中维修申请的原机通过后进入 repair_ready，SKU 不变。继续维修、报废、退供应商分别进入 repair、retired、supplier_returned；退供应商要求原始来源为 supplier。
- 照片使用已存在上传组件及文件存储，验证 ID、URL 和文件字节；检测照片保留在 inspect 事件中，不替换设备入库照片。
- 原机维修返还复用 returned 销售分配，要求 repair_ready、处理中维修申请、订单未取消且机器无其他 reserved/packed/shipped 分配。保存物流单号，将原分配及设备改为 shipped，不新建普通销售履约/订单行，不重复扣库存。
- 检测与维修返还均不自动改数量库存。虽然旧 receive 附近注释提到检测后回补，实际 inspect 分支只更新设备档案与事件，因此按执行代码继承；数量库存后续需独立核对。

## 一致性与操作恢复

业务事务检查当前权限、对象归属及事实版本，再更新设备、分配、事件和收据。结果不明时 UI 冻结原输入并使用同一 UUID 重试；收据绑定原操作者、订单、申请、分配与请求。撤权、设备软删除或转入其他申请后不能借旧收据执行。写入暂停时可恢复原收据。收据或事件失败回滚整个命令。

维修检测通过后仍不能完成售后；返还发货后，原审核完成条件允许关闭申请。新 UI 可再次打开详情读取返还物流单号。
