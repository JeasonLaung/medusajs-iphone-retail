# 仓库用户对象范围

当前交付是仓库用户后续库存/配货命令共用的事务授权入口，不是仓库用户管理或配货闭环验收。

源行为：`medusa-store/apps/backend/src/lib/warehouse-access.ts` 的 `warehouseAccess`、`assertWarehouseLocation` 区分全仓、指定集合与空集合。新系统不导入原用户 metadata、旧角色成员或登录凭证。源 helper 的供应来源限制、履约行裁剪、库存数量裁剪仍需在后续对应业务入口实现，不能用此次仓库 ID 检查代替。

0053 新增 `authorization_warehouse_scopes`，每个新主体显式使用 `selected` 或 `all`；`authorization_warehouse_locations` 持有选定仓库的外键。没有范围记录和空 selected 集合均无访问权；all 不是缺省值。外键保持历史仓库关联，实际授权还要求目标仓库未软删除。范围能力默认关闭，无自动授权。

`authorization.CheckWarehouseTx` 必须在真实调用方事务内、业务锁与操作收据重放之前执行。它校验当前会话代数、账号启用、warehouse 主体、启用角色的显式动作、范围能力开关、最新绑定与有效仓库。当前只接受库存读取、库存调整及履约读取三个已有动作，必须全部满足；商品、全店订单、金额、支付和仓库目录管理动作不能由这个入口放行。

现有 `CheckTx`、全店路由和权限快照保持原边界：仓库主体不获得全店动作。后续专用仓库界面需要自己的权限投影和专用响应字段，不能将本 helper 当作挂到全店接口上的通用 middleware。每个业务命令必须验证其库存行/履约/设备确实属于被校验的仓库；请求中的 location_id 不能证明对象归属。操作多个仓库时逐个校验全部涉及仓库，不能以源仓权限代表目标仓权限。

范围和账号管理命令必须先以 FOR UPDATE 锁住 `authorization_runtime_schema`，再检查管理者当前动作，随后修改主体、范围、角色和绑定。此处的读取持有相同授权行、账号、主体、角色/成员、范围及仓库的共享锁到事务结束。软删除仓库也必须与在途业务的仓库行锁协调。范围更改仍须审计、操作去重、版本冲突处理；本次未提供任意直写 SQL 的管理接口。

验证：隔离 MySQL/Redis 的实际 Gin 认证套件同时运行仓库管理原有测试及新增范围用例，52项迁移完整应用并幂等。覆盖默认关闭、空范围、指定/跨仓、all 有效仓库、软删除/缺失仓库、动作全部必需、不允许全店动作、陈旧身份、禁用账号/角色、撤销动作、缺失范围、旧 RR 快照后的撤销绑定、共享锁阻止管理写入以及拒绝 autocommit。单元验证非ASCII仓库 ID、191字符边界、无效UTF8、控制字符和路径分隔符。Go全包检查与专项结果见 [证据](warehouse-scope-report.json)。

复现：`python retail/scripts/test-admin-auth.py --warehouses-only`。仅使用脚本自建的人工数据库与 Redis，MySQL 单核768MiB、Redis单核128MiB、无发布端口与外部网络；结束清理本次资源。报告明确记录 `http_or_ui_integrated=false`，范围校验本身并未接入专用仓库业务页面。

接续交付：新仓库账号创建/启停和凭证处理、全仓/指定仓库绑定命令及 Ant Design 管理页面、仓库员工登录后的专用可见动作/菜单、范围内库存及配货/发货业务。上述仍属于本期，C04/C07不验收。
