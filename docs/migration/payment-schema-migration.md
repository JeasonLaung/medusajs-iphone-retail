# 正式支付证据结构

2026-10-28。0019_payment_relational.sql 将已审查的支付证据接入显式迁移序列；共 19 个迁移文件。范围为 8 张来源表、83 个来源字段：付款集合、会话、付款、扣款、退款、退款原因、集合/provider 关系及历史付款主体。来源模型、字段和迁移哈希见 `retail/backend/internal/payments/schema_plan.json`，生成器可用 `--check` 检查漂移。

## 数据与边界

金额保持 DECIMAL(38,18) 和原始数值 JSON；状态约束承接来源全部枚举值。六条来源物理外键保持开启，付款的活动 session 唯一性使用软删除条件生成列。来源仅有语义关联的 provider、session、退款原因等不补造物理约束或父记录。历史 provider 标识保留，并不证明其仍可调用。

会话/付款 data、context、metadata 与历史付款主体的受保护字段使用可容纳密文的 LONGTEXT；未受保护的 JSON 列继续要求 JSON_VALID。数据库本身不检查密文真实性，必须经过已审查的专用转换、上下文绑定解密及来源/目标回执验证。SQL NULL 与受保护 JSON null 保持区别。主体的完整 provider/external_id 组合唯一性仍须走已审查的完整值唯一键登记流程，不以明文前缀索引替代。

迁移先检查同名业务表或模型标记；存在时整批拒绝，不改名、采纳或清空原型。启动与健康检查核对编译模型哈希、版本、读取标记及关闭的通用写标记。此标记只表示结构准备完成，不表示数据导入通过或具备支付操作权限。

历史支付导入继续原子写入不可自动解除的 hold。没有新增支付 HTTP 命令、worker、退款/扣款调用或旧账号授权。没有修改源数据，也未连接部署服务器。

## 验证

人工隔离 MySQL 套件验证 19 个迁移的首次执行和重放、8 表/83 字段、超出 JavaScript 安全整数的精确金额、完整状态枚举、JSON/外键拒绝、活动 session 唯一及软删除复用、密文存储、结构漂移与已有表保留。结果见 [后台 SQL 验证](admin-auth-report.json)。扩展套件曾因累计数据库接近临时容器内存上限而超时；测试运行器现按组运行并在每组后清理其人工数据库，保留单核/768 MiB 限制。Docker 超时异常隐藏命令参数，避免输出临时环境变量。
