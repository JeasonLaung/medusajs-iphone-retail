2026-10-30：延伸原 [结账联合](checkout-joint.md)，读取生产 Astro 页面与 Gin 结账处理器实际提交的四笔订单，使用生产订单邮件队列、批准的数据库发信账户、生产 Resend 适配器以及生产恢复命令。MySQL/Redis 均为受资源限制的自有临时实例。未使用 Medusa 或真实客户数据。

## 验证路径

1. 原结账表单依次提交地址、配送和付款；进入隔离的托管付款页面，先返回 pending，再由支付适配器核实 paid，生产 Gin 提交唯一订单、实收及库存预留，原确认页可刷新。四笔订单覆盖 en/zh 和 390/1440 宽度。修正夹具，使两笔中文购物车也持久保存 zh-CN，而不是只切换页面语言。
2. 四笔实际订单各有一条通知意图。邮件 worker 从订单与完成收据关联的真实 payment/capture 读取精确实收 158.75 EUR，验证订单收件人、显示编号和币种。数据库配置账户经显式权限引导和生产保存命令批准；未配置时不选取发件人。
3. 最终邮件 HTTP transport 在测试进程内替换，校验固定 Resend 地址、认证头、发信/回复地址、幂等键、中英文主题及金额。只人工 `.invalid` 收件人；不向外部调用。四个并发 worker 在 SQL 调度门保护下只产生一次初始提供方请求。
4. 第一封邮件在模拟提供方被接收后，连续三次丢失响应，任务自动重试至失败。仅加速独立测试库的重试时间；期间暂时隔离其他测试任务，避免消费无关夹具。通过生产恢复命令重新排队，下一次响应返回同一提供方编号；正文与幂等键完全一致。重放恢复回执不重排已发送任务，恢复审计只有一条。
5. 其余三封发送后，四条任务均持久为 sent。共七次 HTTP 请求、四个唯一提供方消息键、四个独立收件人；数据库冻结正文保持加密，解密后与实际发出的字节一致，提供方编号保持不变。再次运行 worker 不重发。已有结账、权限、金额、库存及 HTTP 隔离回归在同套件继续通过，Go 全包检查通过。

## 验收边界

支付提供方和最终邮件 HTTP 通道为测试替身；没有真实扣款或真实外部邮件收件证据。“唯一提供方消息”指模拟提供方按同一幂等键记录的结果，不能替代 Resend 的实收验收。

此路径预先以生产内部命令建立商品行，尚不包含首页浏览与商品加购、登录购物车转移、仓库配货发货、退款或售后。邮件人工恢复在本次使用生产领域命令；真实 React 后台恢复页面另见 [邮箱联合](mail-joint.md)。C06/C07/C10 与完整前台闭环仍需继续验收。
