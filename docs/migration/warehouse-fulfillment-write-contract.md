# 仓库配货与发货迁移契约

2026-10-30，依据当前源代码确定，尚未实现的要求不能由仓库履约读取测试代替验收。

## 原业务边界

旧 `medusa-store/apps/backend/src/api/warehouse-guards.ts` 的 `authorizeWarehouseCommand` 对仓库账号明确拒绝全店 `assign`、`order_assign`；`save_allocation` 的每个条目必须包含指定包裹，商品属于该包裹，设备与包裹同仓库，修改已有分配时也复核原分配归属。`release` 检查原设备与分配归属，`ship` 检查包裹归属。因此授权订单的一部分不能扩大为整张订单的权限。

旧 `src/workflows/device-operations.ts` 的 `save_allocation` 还包含：已付款、设备 SKU 与订单行一致、设备可售且未重复占用、来源对应设备仓库、仓库关联订单渠道，以及包裹容量检查。已有未发货分配可以换设备；原设备恢复 available；同设备保留分配不重复创建；不能修改已发货/送达/取消包裹。仓库条目不能悄悄转成另建包裹或移动到其他仓库。

旧 `ship` 要求所有设备 packed，设备与包裹位置一致，设备身份有效，所有设备属于同订单，按包裹行逐项核对完整数量，再一次发出整个包裹并保存物流标签。它不是单个设备发货命令，也不能只发包裹的一部分。

## Gin 必须补齐的行为

现有平台 `Allocate` 为订单行预占，`Pack` 创建新包裹并扣减数量库存；现有 `ChangeParcel` 处理整包取消/发货。三者均由全店权限保护。新仓库接口须复用事务内业务校验和设备身份锁，不能通过伪造 employee、临时授予全店权限或先在事务外检查仓库来调用这些入口。

1. 为仓库配货设独立写权限，权限目录、MySQL 约束/模型摘要、新账号编辑器和中英标签同步更新；现有 `order.fulfillment.read` 只读，不自动获得写能力，也不自动给已有角色补写权限。
2. 仓库操作路径始终包含 location/order/fulfillment；当前账号、权限、仓库绑定、目标未删除和包裹当前仓库/订单关系必须在同一事务里校验，并在任何回执重放之前执行。原账号不迁移。
3. 配货候选只返回当前授权仓库、对应 SKU 的可售设备及此包裹已有分配。付款资格内部校验，投影不返回金额、其他仓库候选、成本或全店订单内容。历史已扣数量库存但尚无设备分配的包裹也必须可处理。
4. 保存以包裹当前状态和候选版本生成 revision；操作 UUID、请求冻结和唯一回执沿用现有命令模式。重复请求不重复创建分配、事件或扣减库存；替换已有设备在同一事务释放原设备和占用新设备。分配到已有包裹不再次扣减已履约的数量库存。
5. 复用整包发货的数量/身份/位置校验、标签持久化和站内通知；仓库版响应只返回自己的包裹结果。权限或仓库范围撤销、移仓后，即使持有旧 revision 或操作回执也不能继续访问。取消/释放分别按旧业务允许的入口实现，不能因复用平台取消命令额外授予仓库原来没有的能力。
6. Ant 表单展示包裹行与设备选择；只读账号不显示写动作。网络结果未知时保持同一个命令和正文重试，成功后重新读取；失效 revision 要求刷新。发货必须明确物流单号和完整包裹范围，不能由列表读取或页面加载触发。

## 必须取得的证据

- 真实 Gin/MySQL：双仓共用订单隔离、正确 SKU/来源/渠道/付款、精确数量、超量/重复/外仓设备拒绝、历史包裹关联、换机释放、同内容幂等、并发单胜者、审计/事件失败回滚，以及权限撤销后的回执拒绝。
- 真实 React Admin → Gin → MySQL：平台准备包裹后新建仓库账号，仓库配货/换设备/整包发货并刷新；中文/英文、手机/桌面；授权移除后旧会话失效，重新登录仍不能写；付款与库存记录复核没有重复扣减。
- 原 Astro 订单详情看到相同设备和物流；原购物/回收、旧开发服务持续可用。模拟接口浏览器测试只能补充界面状态覆盖，不能代替上述联合路径。
