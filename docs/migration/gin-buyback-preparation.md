# 回收申请商品与报价快照

`buyback.PrepareSubmission` 是完整申请命令的事务内准备阶段：在调用方的数据库事务中核对既有目录读取基线，重用提交输入校验，按原 handle 或 `swappie-` handle 找到已发布 iPhone，核对实际属于该商品的有效容量选项，再读取当前回收价格及规则。未关联到商品的容量值、已删除关联、草稿/非 iPhone 和不存在的型号不能创建快照。

每台设备保留原 `bbi_` ID 格式、商品和型号快照、原容量和完整问卷，记录当前参考价；最终价和设备绑定为空，检测备注、序列号和 IMEI 为空。报价缺失/禁用维持空参考金额，不替换成零。一台金额为空时整单参考金额为空；否则按原 workflow 的 JavaScript Number 求和后统一保留两位小数，不逐台取整。原精确 raw 金额在逐台快照内继续保留，不通过浮点重写。

公开估价和申请准备共用同一个事务内价格读取函数；公开接口仍维持其原局部问卷校验，完整申请则保留原校验器允许的被跳过字段。调用方必须先验证身份、店铺运行配置和提交去重，再在一致事务中调用准备阶段、写申请及收据。本阶段不自行认证、不提交、不写申请表、不开放 HTTP。

明确的边界：两个有效 iPhone 同时匹配原 handle 和带前缀 handle 时拒绝歧义；原实现使用未指定顺序的第一条，本阶段不会默默按数据库顺序换商品。每台最多读取 1,000 个容量关联，超限拒绝；这不是完整目录无界读取的承诺。

隔离真实 MySQL 验证配置价 294、两台 588、1TB/1024GB 容量等价与合计 314、缺价空总额、草稿/错误标题/软删除关联拒绝、未绑定容量拒绝，以及调用方回滚不留夹具。公开报价原规则/精度/只读和数据库约束回归同时通过；完整 Go 测试通过。金额纯函数另覆盖 1.005、两台 1.005、0.1+0.2 和非法值，保留原最终取整顺序。

申请持久化、客户会话绑定、CSRF、幂等收据、原问卷组件、列表详情、照片、检测、报价确认和付款退回仍待实现。此阶段不构成完整回收提交可用。证据范围及 SHA 见 [报告](buyback-preparation-report.json)。
