# 已核实付款订单的库存预留

2026-10-29，接续 [订单快照](gin-paid-order-snapshot.md) 的 C06 内部事务步骤，尚未提供完整成单接口。

`cart.StagePaidOrderAndStock` 在调用方已有事务中先检查当前购物车/版本/冻结付款及加密实收证据，写入新订单快照并锁定编号器，再按当前商品配送属性、有效配送方式、服务区域、渠道仓库、仓库供应商及库存关系重新规划整车库存。预留数量来自服务端的商品数量与SKU库存需求量，不取客户端数量/仓库/库存标志；预留绑定新订单行，而非购物车行。

已付款购物车维持冻结。内部配送读取使用不导出的上下文标记，仅绑定同一SQL事务、商店、购物车凭证代次、版本和付款操作，嵌套读取仍检查数据库中的当前权限/冻结状态。标记不返回、不传给HTTP或普通修改操作，不暂时清空冻结列。实际普通购物车写入在同一事务内仍拒绝。

最终预留复用 `inventory.ApplyReservations`：按稳定次序锁定库存行，检查库存差异hold、活动预留总和、有效仓库/库存项及可用量，原子写入预留、库存计数和操作收据。允许缺货下单只取当前服务器SKU标志；在途量不是现货。不跟踪库存商品保留配送覆盖检查，但不会伪造库存预留。

订单快照持有编号器锁后再规划库存，使并发新订单遵循一致锁顺序；该实现会串行化编号后的成单事务，尚未进行吞吐压测。事务不得执行渠道调用或实际邮件发送。连接必须是现有Gin数据库配置所用的 `*sql.Tx`；不支持未核对的自定义事务包装器。

## 验证

```powershell
python retail/scripts/test-admin-auth.py --order-snapshot-only
go test ./...
```

在独立目录检查46份正式迁移（不含本地未提交0037通知迁移）。隔离真实MySQL/Redis同时执行旧后台订单读取回归、购物车/地址/配送/付款核实与快照链路，再验证库存集成。实际结果收录 [cart-order-snapshot-runtime-report.json](cart-order-snapshot-runtime-report.json) 的 `order_stock`、`order_snapshot` 和 `existing_order_reader`，附精确源码哈希。完整Go包检查通过。

库存用例使用真实SKU需求量2.5，检查预留指向新订单行/仓库/库存项、预留操作owner和库存计数一致。覆盖默认库存能力关闭、现货不足但在途量999、预留计数与明细不一致、迁移hold、移除渠道仓库/仓库供应商、服务端backorder与不跟踪库存商品。预留操作收据插入阶段注入失败，验证先前已写入的订单/地址/编号/库存计数/预留均回滚；另有4个并发事务分别完整暂存后回滚，确认没有提交状态残留。测试容器禁网、无端口映射且有单核/内存限制，结束后按所有权标签清理。

这些用例没有提交可供客户使用的订单，也不证明最终成单接口已经具备幂等和防超卖联合验收。完整协调器仍须先核对唯一成单收据，再在同一事务完成库存、促销预算、实收记账、购物车关闭、订单归属和通知outbox，成功提交后才对前台确认。任何后续失败都必须回滚整个暂存结果；已付款证据留存供恢复，不能重建付款。前台发起/确认页、真实支付沙箱及配货仍待继续。
