# 客户订单真实联合验证

正式 Astro 页面通过签名桥请求真实 Gin customer/cart/catalog 处理器，连接独立 MySQL 和 Redis；浏览器未拦截或模拟业务 API。隔离副本以 eb995ca 加本次测试代码运行，应用49项迁移，排除工作区尚未提交的 Mollie 通知改动。本轮不改变生产实现或原前台样式。

已验证：

- 浏览器实际登录新客户测试账号，产生 HttpOnly 会话及独立 CSRF Cookie；关联前订单列表为空。
- 原付款确认页以客户会话与本次购物车凭证发起关联；数据库实际保存唯一归属和一条审计记录。
- 删除购物车 Cookie 后，原账号订单列表、详情及近期订单仍可读取已保存商品、SKU、地址和精确金额158.75；刷新可恢复。
- 英文/中文、390/1440宽度均能浏览列表与详情，无横向溢出或浏览器异常；这是交互检查，不是同数据像素对照。
- 另一个新客户登录后列表为空，读取该订单返回404；退出后私有订单接口返回401。私有页面和接口保留 no-store，浏览器不请求 Medusa。
- 浏览器结束后继续执行原 CartRuntime/客户订单权限回归，通过；独立源码副本的 `go test -p 2 ./...` 通过。

测试账号在隔离 SQL 夹具中预先验证，订单由既有付款适配器演练产生。未连接外部支付提供商、未发送邮件，也没有通过整条浏览器购物链发起付款。本轮只验收账户与订单查询/关联的联合路径；购物支付、配货发货、回收、售后、评价和邮件收件仍按[当前交付范围](current-delivery-scope.md)继续推进。

复现使用 `retail/scripts/test-customer-orders-live.py`，需要已存在的 mysql:8.4/redis:7-alpine 镜像、Docker 引擎、Go、Chrome、前端依赖及 Node >=22.23.4（可通过 `STOREFRONT_TEST_NODE` 指定）。脚本只构建新 Astro 应用，创建带唯一归属标签的测试资源：MySQL 1核/768MiB、Redis 1核/128MiB，数据库不发布端口；只发布随机回环 API 端口，网络未限制外连。测试专用夹具端点只编译进测试二进制，需本轮随机密钥；不会进入生产 API。

购物车单元夹具原有 `en` 短语言码，联合验证期间将该夹具的公开目录临时设为已有名称的 `en-GB`，结束恢复，避免伪造公开语言响应。所有容器、网络和测试二进制按归属校验清理；旧开发服务和数据未参与。

结果见 [JSON证据](customer-orders-joint-report.json)。历史[模拟API证据](astro-customer-orders-report.json)保持原记录，不改写成真实联合通过。
