# 售后拒绝至客户查询和通知邮件

本项补 C09/C10 的售后拒绝固定检查点，复用现有 Gin 审核事务、Ant 审核表、Astro 客户申请和正式邮件投递器。没有新增付款、退款、收货或库存动作，也没有把审核状态更新当作退款完成。

来源为 `medusa-store/apps/backend/src/api/admin/orders/[id]/after-sales/validators.ts` 的 `processing/completed/rejected` 状态，以及现有客户售后组件的拒绝显示。原申请原因和商品快照保持。拒绝后客户看到原申请的拒绝状态，不再把它视为处理中申请。

## 固定恢复入口

```powershell
python retail/scripts/test-local-customer-account.py --rejection-mail-from-checkpoint=790ce0fc9e71
```

恢复已证明实收及新账户归属的原订单到独立 `retail_account_<owner>` 库和 Redis 前缀，端口为 19100/19200/19300。关闭结账、付款上下文和退款执行；不再跑购物、付款、配货全链。使用实际客户登录和 Astro 申请、Ant 登录审核、Gin HTTP、MySQL、Redis 和客户查询。邮件外部传输采用隔离 Resend 实现，正式队列、领取、正文冻结、重试及回执仍走生产代码；没有真实收件验收。

验收范围：

- 客户无序列号退货申请丢响应后，同一指令恢复为唯一申请。
- 后台拒绝提交六并发，所有响应相同；丢响应后继续原 UUID/版本/目标状态，只有一条审核收据、一个客户通知和一封业务邮件。
- 关闭开关、停用操作者、旧修订、终态申请、无效状态及不属于该订单的申请被拒绝；相关测试事务全部回滚。
- 在客户通知写入时注入晚故障，审核状态、收据和已经暂存的邮件一起回滚；随后正常拒绝可完成。故障开关仅由测试 harness 在自有数据库安装，应用账户不增加 TRIGGER 权限。
- 已成功指令改内容重放，以及新 UUID 再次操作拒绝终态，正式 HTTP 均拒绝。
- Ant 中英文显示拒绝终态，客户中英文 390px 页面显示同一申请/拒绝状态及唯一通知，无横向溢出。
- 邮件六并发领取仅执行一次；渠道拒绝后由实际后台重试，后台响应丢失继续同指令，发送正文和幂等键保持。
- 订单、金额汇总、原付款/实收/退款、支付会话/集合/日志、账户归属、预留/实物库存、设备及履约前后指纹不变。独立副本、进程及 Redis 键清理，忽略目录保留前后 SQL。

最终证据见 [原生验收记录](after-sales-rejection-native-report.json)。普通 Go 测试只验证包和编译；Windows 检查点需显式运行上述入口。
