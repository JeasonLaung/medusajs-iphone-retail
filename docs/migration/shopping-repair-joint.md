# 新购物订单、原机维修返还与客户查询

本批在上一轮同一新购物订单付款/发货联合之上继续维修路径。外部支付和邮件仍使用隔离适配器；不操作真实订单、设备、库存、付款或收件人，不据此标记 C01–C11 或全部售后完成。

## 客户侧补齐

此前实际维修命令已持久化返还运单，客户售后历史却只有申请状态。本批 `GET /api/store/customer/orders/:id/after-sales` 在原账户/订单归属校验和按本人筛选申请的同一事务内，读取这些申请成功的 `repair_ship` 收据，增加可选 `repair_shipments`。没有返还事实时保持原响应格式。

每条只投影收据 ID、设备 SN（当前设备已软删则为 null）、原样字符串运单和寄回时间。它核对原申请为 repair、原订单/分配/商品行/选中设备、成功结果的 shipped 状态与设备/分配一致。运单取不可变命令收据，不能被后续分配运单覆盖；原销售包裹和其运单仍单独保留。检测照片、说明、员工、来源/仓库、成本和完整命令内容不返回。响应仍为私有 no-store，缺少会话和其他客户的订单仍拒绝。

Astro 严格投影新增可选字段，在原售后申请历史中增加“维修设备已寄回”、SN、返还运单和时间。沿用现有字体、间距和语义文本样式，不添加颜色、边框或新卡片，也不虚构承运商链接或签收状态。原订单查询、售后申请、状态和新申请表单保留。

## 独立联合模式

`CHECKOUT_REPAIR=1` 要求先打开新账号/新购物车/履约模式；它创建的四个新客户各自经过：

1. 实际 Astro 注册/验证/登录、商品加购、地址/配送/付款结果和 EUR 158.75 唯一成单。
2. 实际 Admin 平台配货/装包，指定仓库账号解除、平台重配装包、仓库发货，客户本人查询实际 SN、原销售物流及通知。
3. 客户选择实际已发货设备，提交维修申请；首个成功响应丢失后重试同一命令。
4. 平台受理→按原 SN 收回→上传检测照片并记录原 SKU、成色、电池和检测结果→原机维修通过→登记返还运单→完成申请。收回、检测和返还也分别丢成功响应、重试原命令。
5. 客户刷新本人订单，读取该申请的真实维修返还信息、原销售物流及处理/完成通知；中英×390/1440 全部执行，退出/切换其他客户后订单仍不可读。

只预设隔离数据库中的商品、库存和设备。设备追踪由平台员工通过实际 Admin 启用；为满足真实独享单台库存要求，模式在购物前暂时停用原小数库存测试的共享 SKU 关联，结束恢复。没有预造售后申请、维修、收据、运单、照片或通知业务事实。平台执行收回/检测/返还；这不证明仓库员工已有专用售后收回/检测界面。

运行：

```sh
CHECKOUT_PRODUCT_BROWSE=1 CHECKOUT_FRESH_CART=1 CHECKOUT_ACCOUNTS=1 \
CHECKOUT_FULFILLMENT=1 CHECKOUT_REPAIR=1 \
STOREFRONT_TEST_NODE=/opt/homebrew/bin/node \
ADMIN_TEST_BROWSER='/Applications/Google Chrome.app/Contents/MacOS/Google Chrome' \
python3 retail/scripts/test-customer-orders-live.py --checkout
```

后置 SQL 逐单核对本人唯一维修申请/创建收据、唯一物理收回、一次带真实上传照片的检测、一次原机寄回、完成状态和三条本人已读通知。原销售运单保留，原 SKU/设备不变，维修不改变数量库存；购物/发货原断言和后续付款/邮件恢复回归继续执行。结果独立写入 `shopping-repair-joint-report.json` 并绑定相关源码 SHA-256，脚本清理全部自有容器、网络、二进制和浏览器进程。

仍未完成：实际外部支付/邮件收件、整条换机及差额支付/退款、退货真实退款、仓库专用售后操作、承运商预约/运输/签收，以及当前交付清单其余前台功能。
