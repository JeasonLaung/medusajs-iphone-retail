# 支付全表历史导入

2026-10-28。`paymentimport.Importer` 将 8 张支付来源表、83 个来源字段作为一批同事务暂存：5 张普通证据表/46 字段与 3 张专用受保护策略表/37 字段。全部八个表名必须出现，空表用空切片，拒绝缺表、额外表、重复完整主键和未知字段。来源表顺序按物理外键拓扑排序，同表按完整复合主键的长度前缀编码排序。

## 事务与证据

调用方必须先验证完整来源快照、结构、SHA、全部行数与关系，并在任何错误或后续领域校验失败时回滚。组件只接收已打开的 MySQL 事务，不读源数据库、不执行 DDL、不提交、不访问支付平台。单批上限 100,000 行。完整业务尚未验收时，不得把成功暂存视为全域迁移可上线。

`0020_payment_import_evidence.sql` 新增批次行回执及逐字段缺失关联账本。每行回执包含来源表、完整复合主键与其 SHA、快照 SHA、原始来源行 SHA、首次尝试标识和策略版本；普通行另外保存完整目标行 SHA，并逐列 NULL-safe 读回比较，金额比较显式 CAST DECIMAL(38,18)。同源重复导入仅验证，不覆盖已有业务行。

受保护行不把预检时随机生成的密文当成第二份权威目标 SHA。它们在批次回执中的目标 SHA 必须 SQL NULL，目标真实性由原有专用回执负责：

- payment/payment_session 委托 PaymentHistory.Import；会话 context 仍剥离旧账号绑定/地址簿，原密文解密核对后精确重放，强制 legacy-payment-reconciliation hold。
- account_holder 委托 holderimport.Import；只接受已审查的 system-provider 基线，完整 provider/external_id 组合继续登记完整值唯一性；受保护 data/metadata 保持原密文重放，强制 legacy-account-holder-reconciliation hold。外部标识与邮箱是历史业务证据，不绑定新账号、不恢复保存的付款方式。

所有写入先锁编译模型匹配且读能力开启、通用写能力关闭的 payment_runtime_schema 标记，再按固定顺序锁回执。使用当前锁定读取，避免旧 Repeatable Read 快照遗漏其他事务已提交的导入回执。无需关闭物理外键。

关联检查在全部行暂存后执行，因此 payment 可引用稍后暂存的 session。仅有语义关系的缺失父项如旧 provider、退款原因或币种，不补造父行；保留 parent_domain_unavailable 或 missing_parent、原始来源身份/哈希等事实。released 固定 FALSE，不自动解除原有冻结。状态、金额与历史时间不因 hold 改写。

## 验证

[实际 MySQL 报告](admin-auth-report.json)中的 payment_import 套件使用虚构数据覆盖全部八表，包括同集合两个 provider 的复合主键。覆盖整体回滚、末段关联账本失败回滚、八路同批并发仅一批新写、旧 RR 快照重放、来源/快照/目标精度/hold 篡改拒绝、缺失表与未知保护字段拒绝、密钥轮换保留原密文、缺少旧 key 拒绝、普通/受保护回执的目标哈希 NULL 约束、关闭结构拒绝导入、付款主体完整值唯一性冲突全回滚、来源输入不变及不生成客户/员工账号。

[真实商品/订单隔离演练](catalog-mysql-rehearsal-report.json)将完整支付批次接入已验证的商品/库存/历史客户/订单目标，支付先于订单导入，随后对全部新业务表、各类回执/hold 与唯一键账本做完整指纹比较。实际导入、回滚和原样重放共 95 行：23 集合、21 会话、21 付款、18 扣款、8 退款、3 退款原因、1 历史付款主体；集合/provider 关系表为 0 行，仍保留表键。42 个支付操作 hold 与 1 个付款主体 hold 保留，支付引用差异为 0。支付父项先于订单导入后，新建临时库中的订单引用差异由此前 293 条变为 271 条，22 条原本在来源中存在的付款集合关系已能找到目标父项；这不解除已有目标中的冻结，也不修复完整来源仍有的 375 项缺失引用。

未新增支付查询页面或支付命令。全域事务/恢复协调器、源结构漂移门禁、375 项历史缺失引用处置、持久密钥恢复、provider 对账、完整授权、交易/退款事务和 Astro 仍待完成。T006/T018/T035 与整体支付领域未验收。
