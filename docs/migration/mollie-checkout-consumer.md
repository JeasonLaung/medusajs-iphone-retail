# Mollie 通知到订单的业务消费契约

状态：待实现与验收。0037 收件箱及查询函数已实现；不能据此开放正式收款。

现有正式购物路径由浏览器调用 `ObserveInitialPayment` 查询渠道，再调用 `CompleteCurrentPaidOrder` 完成订单。后者在一个本地事务中建立订单快照、库存预留、促销使用、付款账本、购物车完成回执和订单邮件意图。后台通知必须复用这套业务规则，不能另写一套简化成单逻辑。

## 输入与权限

- 消费入口仅供服务端 worker 使用，不新增允许浏览器提交 remote ID、金额、状态或归属的 API。
- 入口只接受持久观察记录的 attempt UUID。经独立付款密钥认证观察密文，再沿不可覆盖的 remote reference 找到原 effect key、digest 和加密创建请求。
- 必须重新校验 provider、remote ID、cart/session metadata、精确结算金额和币种。不能仅凭通知正文或数据库中的状态字符串确认支付。
- 原请求必须对应当前购物车的同一 checkout attempt、session、collection 和 generation；同时验证 store、活动归属、无支付替换、冻结版本及当前业务开关。旧引用不能转移到新账号、新购物车或新支付尝试。
- 客户关闭页面或不再轮询不应阻止正确的当前尝试完成。SQL 归属已撤销、尝试已替换、金额冲突等情况应保留证据并转人工核查，不能自行修复归属或重新发起付款。

## 事务与重试

- 渠道 GET 在数据库事务之外执行；只有已经验证并持久保存的观察结果才能进入业务消费。
- 提取并共用 `ObserveInitialPayment` 的单调状态合并。`authorized` 不等于已收款；`paid` 不得被延迟的 `pending/open` 降级；互相矛盾的终态要保留核查标记。
- 业务消费事务应锁定当前归属和观察记录，重新授权后保存 checkout 观察证据，更新支付状态；对确认的 `paid` 复用正式成单事务参与函数。订单、付款账本、库存预留、促销使用、邮件意图、完成回执和 `consumed_at` 必须一起提交。
- 对同一通知、重复通知、并行消费、浏览器与 worker 同时成单，最多产生一份订单、付款捕获、预留、邮件意图和完成回执。
- 任意后置写入失败必须回滚整个业务事务，观察记录继续可重试。成功提交后进程崩溃，重试通过原完成回执返回同一订单，不能再次收款。
- 已完成订单收到后续通知仍需验证原绑定。不得改写原创建凭据、删除原付款、重建订单或重复扣减库存；矛盾状态进入核查。
- 未知创建结果缺少 remote reference 的候选发现仍是独立缺口，本消费入口不能用外部 ID 绕过它。

## 必须提供的验收证据

1. 隔离真实 MySQL/Redis 中，客户不返回页面，仅靠通知、权威 GET 和 worker 生成订单；浏览器之后能查看同一订单。
2. `pending/authorized` 不成单，`paid` 成单；延迟通知不降级，终态冲突留核查。
3. 并发通知、并发 worker、浏览器竞争只产生一组业务记录；重复消费不调用创建、扣款或退款接口。
4. 密文篡改、错误密钥、金额/币种/session/cart/digest 不匹配、跨店、旧 generation、已替换尝试、关闭开关全部拒绝，且不标记消费成功。
5. 在订单、库存、付款、促销、邮件和最终消费标记处注入写入失败，证明事务完整回滚及后续恢复。
6. 保持现有中英文、手机/桌面购物浏览器联合通过。真实渠道收款和真实邮件收件分别验收，不以隔离替身代替。
