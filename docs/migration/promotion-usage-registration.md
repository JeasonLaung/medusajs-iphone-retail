# 促销预算登记事务阶段

2026-10-29：`promotion.RegisterUsage`接收服务器已计算的正金额调整项及解析后的promotion ID，在调用方MySQL事务内校验当前有效促销/活动/预算并登记用量。不是独立结账命令，不提交、不提供HTTP，也没有独立幂等回执；不得在普通购物车预览或重算时调用。调用方必须在持有订单/checkout操作身份和幂等锁的情况下调用，任何错误回滚整个事务，成功与同一持久操作回执共同提交。

## 锁与计量

先验证全部输入与金额，再检查正式模型，按ID锁促销、按ID锁活动，再取得对应有效预算的当前锁定读。活动行锁保护预算发现；同一预算的所有合规登记路径都必须遵循该顺序。整个阶段使用最长3秒子context，不修改连接池中的MySQL会话设置。锁后读取不用旧事务快照中的用量；schema行共享锁保护阶段内的启用状态。尚未开放配置编辑命令；将来的配置写入必须遵循相同锁规则，不能绕过预算父锁。

- spend：按同一budget合计所有调整项的精确金额，检查用量加金额不超过limit；要求预算币种与服务器订单币种一致。
- usage：每个不同promotion登记一次，同一promotion的多个商品/运费调整项不重复计数；同一活动多个promotion共同累加同一个预算。
- use_by_attribute：每个不同promotion登记一次。属性取自可信服务器上下文，缺失/空值拒绝；按完整UTF8二进制值比较，大小写、尾部空格、长值不合并。父budget锁串行化首条属性记录创建和重读，重复活动完整值记录拒绝，不猜哪一行有效。全局used同步累计，但额度对属性使用量检查。
- promotion.limit：按一次操作中不同promotion登记一次。没有limit时保留旧used不写，与原分支一致。活动开始时间包含、结束时间不包含，统一使用调用方可信时刻；停用、软删或过期不登记。
- unsupported spend_by_attribute：正式结构允许保留，运行阶段明确拒绝，不能猜成usage或spend。

所有budget修改在执行前完成准备及额度检查；raw优先参与精确运算，不用float。兼容DECIMAL(38,18)只显式截断小数超过18位的部分，完整值以precision100 raw保存。属性值不写入错误或公共结果。写失败/后续失败要求调用方回滚，组件仅返回通用错误分类和更新数量。

## 原行为与明确修正

行为参考实际安装promotion-module的registerUsage与registerCampaignBudgetUsageByAttribute_：有事务要求、稳定顺序父锁、锁后重读、金额/次数/属性区分、属性记录创建与更新。原登记对同promotion多个调整项重复计算相同used+1而最终只写一次；本实现明确按不同promotion汇总一次。原usage共享活动多个code会以相同初始budget.used+1覆盖结果；新实现按不同code累计，修复漏计与超限放行。按属性首行也先检查额度，避免原创建分支直接写1而绕过零额度。资格计算本身已要求属性存在，新登记延续这一约束，不采用旧底层register分支的静默跳过。

## 实库验证与未完成范围

`python retail/scripts/test-admin-auth.py`新增PromotionUsage suite，在独占、无外部网络、1核且限制内存的MySQL/Redis内验证。以最新admin-auth-report.promotion_usage与源码SHA为准，只有字段和SHA均匹配才构成通过证据。测试包括8并发spend唯一成功、8并发属性首创建唯一成功、旧RR快照后锁读拒绝超额、重复调整项、共享活动多code累计、完整属性大小写与尾空格、缺属性拒绝、未知预算拒绝、超18位raw累加、后续失败回滚、预算SQL故障回滚促销计数、活动时间边界、币种错配和autocommit拒绝。该测试不操作真实订单、数据或支付provider。

当前没有预算撤销、操作回执幂等、配置完整值唯一性导入、活动/规则读取组装或完整购物车/结账接入。该阶段依赖调用方回滚和最终持久幂等编排；单独重复调用会再次计数，不能作为对外重试接口。T032/T033/T035未整体验收，通用promotion写能力仍关闭。
