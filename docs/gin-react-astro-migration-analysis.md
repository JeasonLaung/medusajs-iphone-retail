# Gin + React Admin + Astro 迁移架构分析

## 已确认的目标

根据用户最新澄清，最终将现有 Medusa 后端迁移为 Go/Gin。继承的是当前商城的业务规则、功能和数据；最终运行架构不再依赖 Medusa 服务。此前将“购物模块依赖 Medusa”理解成保留 Medusa 运行时的解释已撤回。

- Astro + React 前台：严格保留当前全部页面的样式、URL 和交互，对接 Gin API。
- React 管理后台：外观、布局和基础管理版块参考 iphone0902；商品、订单、设备、售后、回收等能力以当前项目为准，对接 Gin API。
- 后台组件（2026-10-27 已确认）：能用 Ant Design 组件的尽量使用，所有后台图表使用 Apache ECharts；此选型不改变前台严格保留当前页面的要求。
- Gin 后端：承接现有 Medusa 原生交易能力和自定义业务，包括认证、商品、购物车、库存预留、订单、支付、履约、退款、设备、回收及运营功能。
- 数据存储（2026-10-27 已确认）：独立 MySQL + Redis。MySQL 保留业务事实与交易一致性；Redis 承担缓存、限流、会话等临时状态，不作为库存、付款、可靠任务及持久化幂等的唯一存储。当前 PostgreSQL 为只读迁移来源及旧系统运行数据库，逐项完成字段、精度、约束和 SQL 方言转换。
- 账号（2026-10-27 已确认）：不迁移旧客户及员工账号、密码、会话或认证令牌；新系统重新注册/创建账号。历史订单、回收及审计保留必要业务快照和原主体标识，不恢复旧登录身份，不按同邮箱自动把历史业务授予新账号。
- Medusa：在迁移验收期间作为旧系统和业务行为参照；完成切换后退出生产运行。过渡期调用旧接口不构成最终架构依赖，也不允许两套系统无协调地写同一交易。

下面的业务盘点、重写范围、数据继承和逐页迁移分析继续适用。执行任务及验收标准以 [迁移任务清单](gin-react-astro-tasks.md) 为准；用户要求先拆任务，当前暂停新增业务实现，不操作服务器。

日期：2026-10-26。本文为代码审查和架构方案。已提前写入独立后端和导入器草稿、导出只读快照，但未完成业务验收、MySQL 导入或运行切换；不能据此认定迁移完成。

## 1. 结论与边界

建议以当前 Medusa 项目的业务规则、数据、前台页面为产品基线，以 `iphone0902/backend` 的 Gin + React/Ant Design 管理后台为技术参考，建设一个独立的模块化 Go 单体。

前台采用 Astro + React：Astro 负责路由、页面布局、SEO 和适合预渲染的内容；React 保留现有复杂交互。第一阶段允许 Astro 按需渲染，以保住当前登录首屏、账户页、支付返回及动态订单 URL 的行为。逐页验证后再增加静态化比例。

“所有页面严格按照当前”包括：已有 URL、国家与语言切换、文字、字体、图片、组件尺寸、响应式布局、筛选与排序、弹窗、表单反馈、浏览器前进后退、登录和支付返回。更换实现技术不同时进行视觉重设计或业务简化。

不直接把 `iphone0902` 当作新商城代码：参考项目主要是批发目录、询盘、报价和运营系统；审查其路由未找到覆盖本项目购物车、结账、订单履约、设备售后的完整交易链路。

早期方案曾建议保留 PostgreSQL；当前任务按 MySQL 方案拆分，相应增加数据类型、约束、编号及导入对账任务。参考项目的 MySQL/GORM 模型不能直接套在 Medusa 数据上。

### 3.1 容易漏掉的 Medusa 原生能力

只移植 67 个自定义路由远远不够。前台还通过 SDK 调用原生商品、区域、分类、集合、客户、地址、购物车、支付和订单接口。后台的原生页面也由 Medusa 提供，移除框架后不会自动保留。

至少需要补齐：客户认证与邮箱验证、商品/配置管理、销售渠道与区域的有效范围、购物车计算、库存预留、配送选项、税费与促销、支付记录、订单行快照、履约与物流、退货/换机/退款、后台用户与权限、上传和事件处理。

不按依赖包名单认定业务已经使用：例如前台存在 Stripe 相关依赖，但当前后端配置展示的是 Mollie、PayPal 及 PayPal Card；不能据此宣称已有 Stripe 生产支付。礼品卡函数目前是注释占位，不能统计成已完成能力。DHL 接口是固定官方样例，生产环境明确拒绝调用，也不能迁移时写成已接入真实 DHL 物流查询。

博客目前从前台 i18n 数据读取文章，不是完整 CMS。第一阶段应迁移现有内容与展示，而不是顺便更换内容管理方式。

## 4. 设备、库存和售后：优先保住的规则

### 4.1 三层模型要分清

1. 商品 SKU：卖的是什么配置。
2. 库存及预留：某仓/来源还能承诺多少数量。
3. 单台设备及 Assignment：最终是哪台机器交给哪张订单、哪个订单行和哪批履约。

当前 `device-cart-stock.ts` 是兼容性空实现，明确由 Medusa 原生库存和预留验证下单；不能在 Go 中擅自改成“只有登记 IMEI 的设备数量才能下单”。供应商可以先承诺可供量，履约前再登记具体机器。

2026-10-27 深查修正：`deviceStockCaps()` 保留 max/去重计算，但当前找到的非测试调用来自诊断脚本；`reconcile-device-stock.ts` 工作流明确返回空 updates。当前设备登记、供量设置、检测等不据此自动覆盖原生数量库存。Go 应保留设备追踪与数量库存分离的实际行为，不把遗留工具公式重新接入结账或自动同步库存。跨仓移动未发履约的库存迁移、原生履约扣减及取消恢复另行逐动作核对。

### 4.2 需要保留的约束

- 序列号必填；iPhone 至少有一个 IMEI/EID；IMEI 是 15 位文本，EID 是 32 位文本。禁止按数值或浮点存储。
- 身份号码按当前规范化和唯一性规则校验；需专门测试跨 IMEI1/IMEI2 字段冲突，不能仅相信每列单独唯一索引。
- 同一设备只能有一条有效 reserved/packed/shipped 销售分配；数据库约束负责最后防线。
- 普通自有来源的 sale 入库当前直接生成 available 设备档案，returned/recycled 入库生成 inspection；已有 pending/inspection 设备的启用另有动作。档案变为 available 不代表自动增加数量库存。
- 实际成色、电池健康度与所选 SKU 匹配；检测后允许切换到正确 SKU。
- 配货必须匹配订单行、剩余数量、来源和仓库；当前代码要求支付集合 completed，授权本身不能代替已收款。
- 不同来源分批履约；创建履约、库存扣减、剩余预留及设备状态必须一致。
- 取消未发履约恢复库存和设备分配；解除配货及订单取消有不同业务含义。
- 设备退回必须核对原销售记录和真实号码；收回并不直接增加可售库存。
- 原机维修返还不当作重新销售；同 SKU 等价换机保留原机、替换机和原成交价。
- 当前不支持配置升级和差价换机的完整报价支付流程，不能在迁移中假定已有。
- 退款校验所属订单、已实收、已退金额和售后申请；同一申请重试不得重复退款。
- XLSX 每批最多 200 台；预览及任意一行不合法时整批失败，不能改成静默部分成功。
- 流水保留实际操作人、设备、订单、时间和事件内容。

### 4.3 Go 实现方式

订单/库存/设备的单库变更放到显式事务内，通过行锁或条件更新处理竞争，唯一/检查约束兜底；按稳定顺序获取锁，控制超时与死锁重试。先保持当前规则正确，再考虑拆小当前粗粒度设备操作锁。

事务里的每个 repository 必须使用同一个 tx。外部支付、发信、文件服务不放在长数据库事务中等待。为外部副作用记录持久化操作状态和幂等键，通过 outbox/任务表重试、对账；不能用 goroutine 或内存 mutex 代替持久化幂等。

Medusa workflow 的失败补偿不能简单替换成“Gin handler 连续调几个 GORM Save”。GORM 具备显式事务及行锁能力，但业务边界需要自行实现。[事务文档](https://gorm.io/docs/transactions.html)、[行锁文档](https://gorm.io/docs/advanced_query.html)。


每个业务域内部采用 transport/handler → application/service → domain/policy → repository；体量小的域可以合并文件，不强求每域固定四层目录。跨域事务由 application 用例组织，不能让 HTTP handler 承担全部交易逻辑。

部署初期是单个 Go API；任务可以在同一进程中使用有限并发执行，但任务状态、租约、重试和去重持久化。以后有资源再单独运行 worker，同一数据库不能同时启动两套无互斥任务。

数据库迁移延续参考项目“启动不自动建表”的原则，使用可追溯的版本化 SQL；不要在 Go 启动时 AutoMigrate 全部模型，也不修改当前 Medusa 的既有迁移。

### 6.1 API 契约

新接口建议分公共目录、客户会话、Admin、受限入库链接、支付/邮件回调五类；Admin 使用结构稳定的响应封装及分页，Storefront 使用专用 DTO。

可以短期对当前已消费的少量 `/store/*` 或 `/admin/*` 接口提供兼容适配，减小同一阶段 UI 修改，但不要完整仿制 Medusa 任意 fields/query.graph 引擎。建立 API manifest，逐个记录调用页面、角色、请求/响应、错误、幂等和归属校验。

React/Astro 逐步使用项目自己的生成类型/API 客户端。`@medusajs/types` 可以在过渡映射中使用，最终核心领域类型不能依赖已移除的 Medusa。纯展示组件可以暂留 @medusajs/ui/icons，是否替换以视觉回归为准，不在技术迁移时强行替换全部组件。

### 8.1 严格复用页面的做法

1. 先冻结 32 类 URL 和状态清单，选定相同数据、视口、语言、国家及登录状态作为对照。
2. 原样迁移 CSS Modules、样式类、布局结构、品牌字体、图片与 SVG；保持 1200px 内容宽度和当前断点。
3. 初期继续沿用前台现有 Tailwind 配置和相关 UI 组件；参考项目用了不同 Tailwind 配置，不一起升级。
4. 将 `next/link`、`next/image`、router/searchParams、Server Actions、cookies、cache/redirect/notFound 逐项替换；保持其可见行为。
5. 首先保留复杂 React 组件树和 Provider 在同一岛内部，之后才拆分。独立 Astro 岛不能假定共享同一 React Context，购物车、抽屉、结账状态需显式共享或保持同树。[Astro 框架集成](https://docs.astro.build/en/guides/framework-components/)、[岛间状态说明](https://docs.astro.build/en/recipes/sharing-state-islands/)。
6. Ant Design 在当前前台已有使用，需重建其 SSR 样式注入与水合，避免首屏闪烁；不能因 Astro 无 Next AntdRegistry 就删除样式。
7. 保留 country 与 language 的不同含义。现有 `/dk-en`、`/dk-zh` 等 segment 不是纯语言码；`/dk` 会根据当前逻辑重定向。参考项目 `/en/`、`/de/` 的方案不能照搬。
8. 保留 canonical、hreflang、JSON-LD、robots/noindex、站点地图、llms.txt 和站点验证文件，旧 URL 的重定向要逐条验证。

静态页面不会自动获得访问者的私有 Cookie 数据，订单 ID/token 等无限动态 URL 也不能靠预先枚举全部生成解决。纯静态账户壳 + 客户端请求可作为后续选项，但首屏和加载反馈需要单独验收。Astro 官方支持预渲染与按需渲染结合；使用 Node adapter 的 SSR 仍需常驻 Node，不能承诺改为 Astro 后一定消除 Node 运行内存。[按需渲染说明](https://docs.astro.build/en/guides/on-demand-rendering/)。

### 8.2 会话与支付返回

推荐前台域名同源代理 `/api` 到 Go，客户登录采用 HttpOnly/Secure Cookie 会话，写操作校验 CSRF/Origin；不把现有服务端 JWT 转成前台任意可读的 localStorage token。Admin 与 customer 会话、权限和 Cookie 范围独立。

保留支付跨站返回所需的 SameSite=Lax 语义、独立支付尝试引用、多标签页与已完成购物车恢复。`/api/mollie-return` 和 `/api/payment-return` 的旧 URL 及参数需有兼容处理。浏览器回跳不作为付款证据，后端按 provider 规则核验并处理重复、乱序、网络超时与退款。

## 9. 数据继承与数据库设计

建议另建 Go 数据库，在副本导入演练，不让 Go 与 Medusa 同时写当前业务库。先定义新业务表及兼容 DTO，再导入，不将全部 Medusa 系统表机械复制为新领域模型。

| 数据组 | 迁移与校验要求 |
| --- | --- |
| 商品/SKU/选项/图片/价格 | 保留原 ID 或唯一 legacy_id 映射、handle、SKU、历史 metadata、图片排序、选项组合和币种 |
| 区域/渠道/税/运费/促销 | 导出真实配置和使用情况，明确当前生效规则；不硬编码为欧元单地区固定运费 |
| 订单/订单行/地址/金额 | 保留旧 ID、展示号、状态、成交价格、税、运费、优惠、退款与历史名称快照 |
| 支付/退款/履约/退货/换机 | 保留 provider 侧 ID、金额、事件关联；历史订单不能只剩一张汇总表 |
| 设备/来源/供应量/分配/事件 | 保留软删除、位置、来源、订单行关联、替换机关系、售后关联、身份唯一性 |
| 客户/Admin/权限 | 不导入旧登录账号、密码、会话、认证令牌及个人权限；重新注册客户和初始化员工。历史业务保留原主体标识及必要快照；新账号不按相同邮箱自动取得历史业务权限 |
| 回收/报价/照片 | 保留申请 item ID、问卷、报价规则、终价、历史、照片 storage_key、审核与失效规则 |
| 邮件/通知/评价/SEO | 保留发送和接收事件 ID、退订与订阅状态、去重键、审核、页面 URL 和监测配置 |
| 密钥和文件 | 旧密文格式先验证兼容，再安全转换；公开/私有文件分别迁移，备份密钥及配置不写进仓库 |

### 9.1 金额、标识和编号

Medusa 的商品价、订单价及回收价使用主要货币单位，而 Device.cost_cents 明确使用分；必须按字段映射，不能统一乘/除 100。Go 使用 decimal/数据库 NUMERIC 或明确的最小单位整数，禁止交易金额用 float64。税费/折扣的精度与舍入按当前实际输出固化测试。

19 位订单展示号必须以字符串贯穿数据库、API 和 React；不能经 JavaScript Number 中转。现有订单编号由 PostgreSQL trigger/分配表在事务内产生，包含上海时区及防冲突逻辑；SKU 的 ERP 编号也有数据库触发器和计数器，不在普通业务模型里。迁移必须继承历史号和下一次分配位置，保留自定义 SKU，禁止重号或重排历史编号。

参考项目的 uint ID 和 MySQL 自增值不作为替换历史业务 ID 的理由。新表可以保留原字符串 ID；确需新 ID 时保留稳定唯一映射，旧链接通过映射解析。

### 9.2 对账与切换

1. 固化只读快照和文件清单；原库保持服务，迁移阶段不生成真实付款/发信副作用。
2. 新库可重复导入，记录运行 ID、源 ID、目标 ID、校验和、错误及进度；重复导入不重复创建业务记录。
3. 对比所有有效及软删除记录、孤立关联、订单金额汇总、支付/退款、库存和预留、活跃设备分配、文件哈希；客户后台视图与管理员视图分别对账。
4. 在独立环境完成下单到售后、回收到付款/退回的整链路回归。
5. 正式切换前设置短暂写入维护窗口，停止旧任务消费者、做最终增量和对账；支付回调应排队/重试或路由到明确的唯一处理方。
6. 切换后新系统是唯一写入者。回滚不能只切 Nginx 或旧程序：新系统已有订单、退款或库存变化时，需要增量回放/对账及明确的退款执行归属。

不能声称“有旧数据库备份就能随时一键回滚且不丢交易”。

| 6 迁移演练与切换 | 导入器、对账报表、压测、发布和回滚演练 | 全链路与资源峰值达标，具备最终增量及回调接管方案后才上线 |

阶段 2 的前台样板用于验证技术路线；业务 API 和数据适配尚未完整前，不把它视为可上线商城。旧系统持续可用，新系统在隔离库逐步实现，不在生产边跑边替换同一订单的不同写入步骤。

### 10.1 关键验收用例

- 相同 SKU 最后一件库存的并发下单；同一设备两名员工同时配货；同一订单不同来源混合履约。
- 配货后取消履约、解除配货、订单取消的库存/预留/设备恢复；未付款不得配货。
- 供应商在没有设备号码时的数量承诺和随后登记，证明不重复增加库存。
- 整批入库任意一行失败不残留；15/32 位号码、跨列冲突、软删除后重新入库按当前规则处理。
- 退回号码不匹配拒绝；维修返还不上销售库存；换机保留原价与替换关联。
- 退款请求超时后重试、重复回调和重复点击；金额不超实收、不重复退款。
- 回收问卷相同输入得到相同报价，照片审核不通过、终价被拒绝、付款/退回的合法转换。
- 仓库跨范围、供应商跨来源、客户跨订单、私有附件直链访问均被拒绝；无采购成本泄漏。
- 支付跨站返回、旧回跳链接、不同标签页、已完成购物车、回调先/后于浏览器返回。
- 国家与语言切换、搜索参数和分页、抽屉/弹窗、错误状态、空态、加载态、刷新/后退保持当前体验。
- 以固定数据在 390px 手机、768px 平板、1440px 桌面比较中英文；遮罩仅限时间/随机 ID，不能遮掉商品、金额或布局差异。
- SEO 原始 HTML 含标题、商品与结构化数据；账户/购物车/订单等继续 noindex，缓存不混入其他客户数据。

现有 48 个顶层单测和 scripts/check-* 是业务规范素材，需要按规则重写为 Go/端到端测试；不能机械复制 mock 并把通过当作迁移完成。

## 11. 资源与发布策略

最终 Go + 静态 React Admin + 以静态为主的 Astro，理论上可降低当前 Node 电商后端与 Next 运行开销；具体节省必须实测。第一阶段混合 SSR 仍有 Astro 运行时，不能提前按“完全没有 Node”选机器。

保留 GitHub 构建、独立前后端产物、按路径触发发布、串行部署、健康检查和版本回退。Go 可发布二进制由 systemd 管理，也可容器运行；Docker 与资源隔离并不冲突，不能把此次容量事故归因于 Docker 本身。

公共内容改动可触发受控构建或发布新内容快照；库存/价格/订单的每次变动不能靠全站重建更新。商品即时下架和价格新鲜度需要明确缓存失效方案。公开快照只包含允许公开的数据，不能打包客户或私有配置。

API、数据库、SSR、日志、连接池、上传解码/缩图和后台任务都要分别纳入内存与 CPU 峰值预算。参考项目的爬虫、SEO 扫描、在线 npm build、群发邮件等资源重任务不能默认同时启动。GOMEMLIMIT 是 Go runtime 的软限制，不等于整机内存保障。

本次不操作曾失联的服务器。实际服务器恢复与容量评估是后续独立工作，不因架构方案成形就自动启动旧部署或新服务。

## 12. 需要在实施前进一步确认的内容

以下是调查待办，不影响本方案的方向，也不代表要求现在中断分析等待确认：

- Medusa 原生 Admin 哪些设置实际使用：促销、税率、价格表、订单编辑、草稿单、API key、销售渠道等；仅凭自定义目录不能证明未使用。
- 当前真实支付商户和历史支付未结清状态；新 Go 适配是否支持相同能力、旧交易退款及回调验证。
- 新账号会话生命周期及员工初始化流程；旧账号不迁移已确认，无需再调查旧密码兼容方案。历史业务主体映射须与新登录身份隔离。
- 全部 JSON metadata、原生关联表、订单版本/调整明细、软删除和编号触发器的逐字段映射。
- Astro SSR 与静态化各页面的首屏/动态新鲜度要求，全部页面截图和交互状态基线。
- 参考项目可复用组件的逐文件依赖审查；当前只核对了结构和代表性实现，没有把整个参考项目做完整安全审计。

建议下一份实施文档是“业务域 × 数据表 × API × Admin 页面 × Storefront 页面 × 验收用例”的追踪矩阵，先覆盖一条商品到下单/设备履约/售后的完整纵向链路，再据此排每批改造。
